# Server (`apps/server`)

NestJS 12 + TypeScript 6, **native ESM** (`"type": "module"`), Express platform.

## TypeScript / ESM

- `moduleResolution: nodenext`, emits native ESM. Relative imports **must** carry a `.js` extension; directory imports point at `./dir/index.js`. Use `import.meta.dirname` instead of `__dirname`.
- `emitDecoratorMetadata` + `experimentalDecorators` are required for Nest DI.
- TS 6 turns `strict` on by default — kept on, except `strictPropertyInitialization: false` (DTO fields are filled by class-transformer, not constructors).
- `types` must be listed explicitly (TS 6 default is `[]`).
- `tsconfig.build.json` pins `rootDir: ./src` (and excludes `drizzle.config.ts`, `vitest.config*.ts`) so `nest build` emits into `dist/`, not `dist/src/`. `tsBuildInfoFile` is pinned into `dist/` too, otherwise TS 6 drops it next to the config.
- Don't unify this config with `apps/web`'s — they differ by design.

## Logging

`nestjs-pino`, configured in `src/app.module.ts`, attached in `src/main.ts` via `app.useLogger(app.get(Logger))` with `bufferLogs: true`. Two targets:

- console: pretty-printed in dev, raw JSON when `NODE_ENV=production`;
- always also `apps/server/logs/app.log` as plain text (no ANSI codes), so past runs can be inspected without re-running. `logs/` is gitignored.

`LOG_LEVEL` controls the level (default `info`). Cookie headers are redacted. Usage rules for services are in [CLAUDE.md](../CLAUDE.md#logging-apps-server).

## Database

Drizzle ORM (`drizzle-orm/node-postgres`, `pg` driver) against Postgres.

- `DatabaseModule` (`src/database/`) is `@Global()` and exports `DatabaseService`: owns the `pg.Pool` and the drizzle instance (`databaseService.db`), checks connectivity with `select 1` in `onModuleInit`, closes the pool in `onModuleDestroy`.
- Schema: `src/database/schema/`, one file per table (`users.ts`, `refresh-tokens.ts`, `characters.ts`, …) plus an `index.ts` barrel (what `import * as schema` in `database.service.ts` resolves to). Add new tables as new files there. A new table file must also go into the list in `drizzle.config.ts`, or `db:generate` silently leaves it out.
- `drizzle.config.ts` lists the individual table files (not the barrel) so drizzle-kit doesn't see tables twice. It runs outside Nest DI, so it loads `DATABASE_URL` itself via `import 'dotenv/config'`.
- `DATABASE_URL` comes from `apps/server/.env` (gitignored; shape in `.env.example`), read through `ConfigModule.forRoot({ isGlobal: true })`. Never hardcode it.
- **Migrations are not run on boot.** `pnpm db:generate` writes a migration into `apps/server/drizzle/`, `pnpm db:migrate` applies it. A schema change must come with its migration.
- **Hybrid entity schema** (`characters`): frequently point-updated scalars (HP, AC, ability scores, death saves…) are real columns; variable-length nested data (spells, features, proficiencies…) is `jsonb` typed via `.$type<T>()` against `packages/shared/src/character.ts`. Use the same split for future entities shaped "fixed core + variable nested lists". Lists that point at other rows (the inventory, which references catalog items) get their own table with foreign keys instead.

## HTTP surface

- All routes live under `/api` (`app.setGlobalPrefix('api')`) — in production the SPA is served from the same origin, and its client routes (`/characters`) would otherwise collide with API routes.
- `src/web-app.module.ts` registers `@nestjs/serve-static` only when `apps/server/public` exists (the Docker image copies `apps/web/dist` there), excluding `/api/{*path}` so unknown API routes stay JSON 404s. In dev/tests it's a no-op.
- Global `ValidationPipe({ whitelist: true, transform: true })` — DTOs in `*/dto/` use class-validator.
- Profile (`/profile`, `AuthGuard` + throttler 10/min, `auth/profile/`): `GET` returns `{ login, nickname, hasPassword, providers }` (`login` is `null` while there is no password: the technical `lolka_…` login means nothing to the person); `PUT /credentials` gives a passwordless account its own login and password (the `UPDATE` itself requires `password_hash IS NULL`; a taken login is 409 «Этот логин уже занят») and re-issues the session cookies, since the login sits in the JWT; `POST /password` changes the password given the current one (a wrong one is 400, not 401, so the web doesn't take it for an expired session).
- Settings (`/profile/settings`, `AuthGuard` only — a separate `ProfileSettingsController`, since the profile's 10/min limit guards the password and settings get toggled often): `GET` returns the user's `UserSettings` (`shared/userSettings.ts`: so far `facingMarker` — `pointer`, `chevrons` or `compass`, how the map shows facing); `PATCH` takes any subset of the fields (an unknown value is 400 «Неизвестный вид отметки взгляда», unknown fields are stripped) and returns the whole settings. They are stored in `users.settings` (jsonb, `{}` by default) and merged in the `UPDATE` itself (`settings || patch`), so two changes of different fields don't overwrite each other; reads go through `readUserSettings`, which fills defaults and drops invalid values. The same settings come with the user from `login`, `register` and `GET /auth/me`, so the web knows them from the first screen.
- Characters (`/characters`, all behind `AuthGuard`): `GET` lists the user's own by `updatedAt` desc (`$onUpdate` bumps it on every ORM update), `POST` creates, `PUT /:id` is the full-sheet edit with `CreateCharacterDto` (keys absent from the payload stay untouched, so in-game fields like death saves survive; keep the DTO free of default initializers), `PATCH /:id` is the narrow in-game update (`UpdateCharacterDto`), `DELETE /:id`.
  - Spell slots: `spell_slots` holds per circle `{ total, expended }` (`total` at most 9, an app limit). The form sets it through `PUT`; `PATCH` `{ spellSlotsExpended: { "1": 2 } }` sets only the spent count of the circles sent, computed by `spendSpellSlots` (shared) on the row read `FOR UPDATE` in the same transaction, so quick clicks don't overwrite each other. More spent than the circle has (0 for a circle without slots) is a 400 «Ячеек N круга меньше, чем потрачено». Plan: [plan/done/character-abilities.md](plan/done/character-abilities.md).
  - Type (`characters.kind`, migration `0034`): `'pc'` (default) or `'npc'`, an NPC is the GM's character with the same sheet. `POST` and `PUT` take an optional `kind` (anything else is 400 «Персонаж бывает только игровым или НПС»); a `PUT` without it keeps the current type. `GET /characters` returns both kinds, the list splits them in the browser. Plan: [plan/done/monsters-npcs.md](plan/done/monsters-npcs.md), stage 8.
  - Sharing by link: `characters.link_access` is `'private'` (default) or `'link'`. `GET /:id` returns the character to its author, or to any signed-in user when it is `'link'`; a private character of someone else is a 404, like a missing one. Every write (`PUT`, `PATCH`, `DELETE`, the gallery edits) stays author-only. `PUT /:id/access` `{ linkAccess }` is the author's switch; it keeps `updatedAt`, so sharing does not reorder the list, and the full-sheet `PUT` never touches the access. Responses carry `linkAccess` and `authorNickname`. Plan: [plan/done/character-sharing.md](plan/done/character-sharing.md).
- Character images (`/characters/:characterId/images`, `AuthGuard`). The list and the files are readable by whoever can open the character (`assertViewableCharacter`), uploads and edits are owner only (`assertOwnedCharacter`); a character the user can't open is a 404 «Персонаж не найден». Plan and decisions: [plan/done/character-images.md](plan/done/character-images.md).
  - `GET` lists the gallery metadata, `POST` takes one `multipart/form-data` file (field `file`, multer memory storage, 10 MB, 40 uploads a minute per IP), `PATCH /:imageId` sets `{ isMain: true }` and/or `{ thumbCrop }`, `DELETE /:imageId` removes it (if it was the main one, the next by position becomes main).
  - `GET /:imageId/file?variant=full|preview|thumb` returns the WebP bytes with `Cache-Control: private, max-age=31536000, immutable`; the client adds `&v=<thumbVersion>` for the thumbnail, whose bytes change on a new crop. The web fetches these through `fetch`, not `<img src>`, because an image tag can't refresh an expired session.
  - The upload is never stored as is: the shared core `images/decode-image.ts` (also used by item images) re-encodes it with `sharp` into `full`, and `image-processing.ts` adds the rest — three WebP variants (`full` ≤ 2048 px, `preview` ≤ 480 px, `thumb` 256×256), which also checks the real format (JPEG, PNG, WebP), applies the EXIF rotation and drops the metadata. A file `sharp` can't read is a 400; a file over the limit is a 413 with a Russian message (`images/upload-too-large.filter.ts`, since multer's own text is English). The size limit and the formats are `IMAGE_MAX_BYTES` and `IMAGE_MIME_TYPES` in `shared`.
  - Tables: `character_images` (metadata, `thumb_crop` jsonb in pixels of the `full` variant, a partial unique index keeps one main image per character) and `character_image_files` (`bytea`, one row per variant). Bytes live in Postgres because dev and prod share one database (see [deploy.md](deploy.md)): a file on a local disk would not exist in production. Edits run in a transaction that locks the character row, so the limit of 20 images, the positions and the single main image survive parallel requests.
  - `Character.mainImage` (`{ id, thumbVersion } | null`) is filled by `loadMainImages` in the characters service.
- Character inventory (`/characters/:characterId/items`, `AuthGuard`, `characters/inventory/`). Plan: [plan/done/character-inventory.md](plan/done/character-inventory.md); carrying capacity: [dnd/carrying.md](dnd/carrying.md).
  - Table `character_items`: a row links a catalog item (`item_id`, `ON DELETE SET NULL`) with a `location` (`carried` or `stash`) and a `quantity` (1–9999); one row per item and place (unique `(character_id, item_id, location)`), ordered by `added_at`.
  - The inventory is read with the sheet: `Character.inventory` comes from `loadInventories` as the viewer sees it. A row whose item the viewer can't see is `{ item: null, missing: 'hidden' }` with no card data at all (not even the id or the weight). A row whose item the character's owner can't see (only its author, looking at the shared sheet, gets here) keeps its card but has `inactive: true`: the author always sees their own items, yet a hidden item doesn't act on the character, so `carriedLoad` leaves it out and a viewer's load never exceeds the owner's; a row whose item was deleted is `missing: 'deleted'`. The load is summed on the client (`carriedLoad` in `shared`), never sent by the server, so a total can't reveal a hidden item's weight.
  - Writes are author-only (another user's character, even shared by link, is a 404) and each returns the whole inventory: `POST` `{ itemId, quantity, location, unpack? }` adds an item the author can see (otherwise 400 «Предмет не найден»); with `unpack: true` a pack goes in as its contents, each row × `quantity` (`inventory-unpack.ts`), leaving out contained items the author can't see; unpacking a non-pack, or a pack with nothing visible inside, is a 400. The rows of one unpack get `added_at` a millisecond apart, so they keep the pack's order; the same item in the same place adds to the row atomically (`ON CONFLICT DO UPDATE`), and going over 9999 is caught from the check constraint as a 400. `PATCH /:entryId` `{ quantity?, location? }` changes a row; moving it where the same item already lies merges the two rows, under a lock on the character row. `POST /:entryId/move` `{ location, quantity }` moves part of a stack (or all of it) to the other place in one transaction: the rest stays, the part joins the same item's row there or starts a new one. Hidden and deleted rows can only be removed (`PATCH` and `move` on them are a 400). `DELETE /:entryId`.
  - The old free-text jsonb column `characters.inventory` was dropped by migration `0021` (it first checks every list is empty). A column the running server still selects can't be dropped in the same deploy as the code that stops selecting it: deploy the code first, then the drop.
- Effects on a character (`/characters/:characterId/effects`, `AuthGuard`, `characters/effects/`). Plan: [plan/done/character-effects.md](plan/done/character-effects.md).
  - Table `character_effects`: a row links a catalog effect (`effect_id`, `ON DELETE SET NULL`), ordered by `added_at`; one row per effect (unique `(character_id, effect_id)`), since the same spell doesn't stack. No remaining duration is stored yet: the player removes the effect.
  - Read with the sheet and the list as `Character.effects` (`loadCharacterEffectLists`), by the same visibility rules as inventory rows: `missing: 'hidden'` with no card data, `inactive: true` for the effect's author looking at a sheet whose owner can't see it, `missing: 'deleted'`. The card carries the components, duration and save-ends, so the sheet can compute the totals in `shared`. The form values (`armorClass`, `speed`) are the base without effects.
  - Writes are author-only (another user's character, even shared by link, is a 404) and return the whole list: `POST` `{ effectId }` applies an effect the author can see (otherwise 400 «Эффект не найден»; already applied — 409 «Эффект уже наложен», via `ON CONFLICT DO NOTHING`); `DELETE /:entryId` removes any row, hidden and deleted ones included.
- Abilities on a character (`/characters/:characterId/abilities`, `AuthGuard`, `characters/abilities/`). Plan: [plan/done/character-abilities.md](plan/done/character-abilities.md).
  - Table `character_abilities`: a row links a catalog ability (`ability_id`, `ON DELETE SET NULL`) with a `prepared` flag, ordered by `added_at`; one row per ability (unique `(character_id, ability_id)`).
  - Read with the sheet and the list as `Character.abilities` (`loadCharacterAbilityLists`), by the same visibility rules as effects (`missing: 'hidden' | 'deleted'`, `inactive`; the shared mapper is `abilities/ability-link.ts`, also used by monsters). The card carries only what the sheet groups and labels by: category, spell `level` (`null` otherwise), activation, costs and `recharge` (a «Монстра» ability's, `null` otherwise).
  - Writes are author-only (another user's character, even shared by link, is a 404) and return the whole list: `POST` `{ abilityId }` adds an ability the author can see (otherwise 400 «Способность не найдена»; already added — 409 «Способность уже добавлена»); `PATCH /:entryId` `{ prepared }` — `true` only for a spell of circle 1+ the author can see (`canBePrepared` in shared, otherwise 400 «Подготовить можно только заклинание 1 круга и выше»), `false` always; `DELETE /:entryId` removes any row.
- Items (`/items`, `AuthGuard`, `items` module) — a shared catalog with authors. Plan and decisions: [plan/done/items.md](plan/done/items.md); rules data: [dnd/items.md](dnd/items.md).
  - `GET /items?scope=mine|catalog` lists the author's own items (hidden ones too) or every published item; `POST` creates, `GET /:id`, `PUT /:id` (full edit, the same `ItemDto`), `DELETE /:id`. Each item carries the author's nickname (a join on `users`).
  - Access (`item-access.ts`, on top of the shared `catalog/catalog-access.ts`): the author sees and edits their item; others see it only when `is_public`. Another user's hidden item is a 404 «Предмет не найден»; editing or deleting another user's published item is a 403 «Менять предмет может только его автор».
  - Table `items`: common fields as columns (`weight` is `numeric(8, 2)` read in drizzle's `mode: 'number'`; the cost is `cost_amount` + `cost_coin`, a check constraint keeps them both set or both null), `rarity` is required, `none` (a mundane item) by default; the category's own fields in `details` jsonb. `DetailsForCategory` checks `details` against the category; categories without their own fields (`PLAIN_ITEM_CATEGORIES` in `shared`: basic, material, quest) have an empty object; food has `{ satiety }`, an integer 0–1000; treasure has `{ kind }`, one of `TREASURE_KINDS` (gem, art, trade_good); a container has `{ capacity }`, pounds above 0 to hundredths, or null when not given. `toItemVariant` in the mapper reads food saved before that field as satiety 0 instead of migrating the rows, and an unknown treasure kind as `trade_good`.
  - Equipment packs (category `pack`, plan [plan/done/item-packs.md](plan/done/item-packs.md)): in the API a pack's `details` is `{ contents }`, other catalog items with a quantity. The body sends `{ itemId, quantity }[]`: 1–50 distinct items, quantity an integer 1–1000. Responses add `item`, a short card (`name`, `category`, `weight`, `isPublic`, `image`). That card is `null` when the item's author hid it from the reader. The list and the item card both resolve contents (`PackContentsService.resolve`, one query per request).
    - Storage: the contents live in table `item_pack_entries` (migration `0018`), not in `items.details`, which stays `{}` for a pack. The table has `pack_id` and `item_id`, both foreign keys to `items` with `ON DELETE CASCADE`: deleting an item removes it from every pack. `position` keeps the author's order, and the primary key `(pack_id, item_id)` allows one row per item.
    - Writes: `POST`/`PUT` write the item and replace its rows in one transaction. A non-pack item keeps no rows, so changing the category drops them.
    - Errors, all 400:
      - «Предмет из состава набора не найден»: the item doesn't exist or is someone else's hidden item.
      - «Набор нельзя положить в другой набор»: the contents include a pack.
      - «Предмет лежит в наборах — набором он стать не может»: an item already inside a pack is being made a pack.
    - Publishing: a pack can be public only when everything in it is public. Saving a public pack with the author's own hidden items is a 409 «Сначала опубликуйте предметы из состава: …», with the item names. With `publishContents: true` in the same body, the server publishes those items in the same transaction instead.
    - Hiding: an item inside packs can still be hidden. Other users' packs stay public, and their row shows `item: null` to readers. With `hidePacks: true` in the body of a `PUT` that hides the item, the author's own public packs containing it are hidden in the same transaction (`PackUsageService.hideOwnPacks`). Both flags belong to the request and are not stored.
    - `GET /items/:id` (and the create/edit responses) adds `packs: { mine: { id, name, isPublic }[], othersCount }` for the item's author only: where the item lies, for the delete and hide confirmations. Other users' packs are a count, since their names may be hidden. Next to it, `holders: { mine: { id, name }[], othersCount }` (`ItemHoldersService`) says which characters carry the item, own ones by name and other users' as a count.
  - Item image (`/items/:ownerId/image`, `item-images` module, on top of the shared catalog image code — see «Catalogs» below): one image per item. `PUT` uploads or replaces it (multipart field `file`, same limits, throttle and 413 filter as character images), `PATCH` `{ thumbCrop }` re-cuts the thumbnail, `DELETE` removes it — all author-only (403/404 as for the item, checked before `sharp` runs). `GET ?variant=full|thumb` returns WebP bytes to anyone who sees the item, `private, max-age=31536000, immutable`; the client adds `&v=<version>`, and `version` grows on every replace and re-cut.
  - Two variants only: `full` (≤ 2048 px) and `thumb` (256×256). The thumbnail crop may reach past the image edges (`x`/`y` negative, `size` up to twice the long side, but it must overlap the image): the margins are transparent, so a long sword fits whole. The default crop is the whole image centred. `renderCatalogThumb` cuts the overlap, scales it and lays it on a transparent 256×256 canvas, never a canvas the size of the crop.
  - Tables `item_images` (key `item_id`, size of `full`, `thumb_crop`, `version`) and `item_image_files` (`bytea` per variant). Writes lock the item row (`FOR UPDATE`), so two uploads can't mix one's metadata with the other's bytes. `Item.image` (`{ version, width, height, thumbCrop } | null`) comes from a left join in the items service.
- Catalogs: the shared code behind items, abilities and effects (`catalog/`, plan [plan/done/abilities-effects.md](plan/done/abilities-effects.md)). Each catalog subclasses the generic pieces with its own tables, texts and `@InjectPinoLogger` context; Nest reads route and parameter decorators through the class chain, so a subclass only declares its `@Controller` path, `AuthGuard` and constructor.
  - Access (`catalog-access.ts`): `CatalogAccess` names the table, its `id`/`author_id`/`is_public` columns and the 404/403 texts; `visibleEntry`, `authoredEntry`, `rejectCatalogEdit` (403 for another user's public entry, else 404) and `lockAuthoredEntry` (`FOR UPDATE`) work on any catalog.
  - Tables come from factories in `database/schema/catalog-tables.ts`: `catalogEntryTable(name)` (columns as in `items` minus weight, cost and rarity, plus `extra` jsonb for fields every entry of one catalog has and the others don't, migration `0023`) and `catalogImageTables(prefix, ownerColumn, ownerId)` (the `<prefix>_images` and `<prefix>_image_files` pair). The table name is a plain string, so every table of a factory has the same type and the generic code is typed. The image pair's key column is `ownerId` in code and `item_id`/`ability_id`/`effect_id` in the database; items use the same factory, with no change to their tables.
  - Images (`catalog/images/`): `CatalogImageEditService` (upload, re-cut, delete), `CatalogImageFilesService` (bytes) and `CatalogImagesController` (`/<catalog>/:ownerId/image`), driven by a `CatalogImageConfig`. Behaviour as for item images above.
  - Simple catalogs (`catalog/entries/`): `CatalogEntriesService` and `CatalogEntriesController` give `GET ?scope=mine|catalog` (`ListCatalogQueryDto`), `GET /:id`, `DELETE /:id`; the subclass declares `POST` and `PUT /:id` itself, because the body is checked by its own DTO class (`CatalogEntryDto` plus the catalog's own fields). The config's `toVariant(category, details, extra)` reads the catalog's own fields from the row and `toStored(dto)` lays them out into the `category`, `details` and `extra` columns. `CategoryDetails` checks `details` per category for the catalogs that have categories, items included. A catalog with links to other rows sets the optional `writeLinks` (run in the same transaction as the insert or update, so a rejected link leaves nothing behind) and `attachLinks` (run after the list and the card are read) in its service class.
- Abilities (`/abilities`, `abilities` module) and effects (`/effects`, `effects` module): simple catalogs with the same access as items (migration `0022`). Common fields: `name` (1–100), `description` (up to 5000), `isPublic`; images at `/abilities/:id/image` and `/effects/:id/image`. Abilities have `category` and `details`: one category, `basic`, whose `details` is an empty object, and required `activation` and `costs` (stored in `extra`, checked by `isAbilityActivation`/`isAbilityCosts` from `shared`; rows without them read as an action with no costs), see [dnd/ability-usage.md](dnd/ability-usage.md). Effects have no category: an effect is a required list `components` (up to 20, checked by `isEffectComponents` from `shared`: `{ kind: 'sense', sense, range }`, see [dnd/senses.md](dnd/senses.md), `{ kind: 'condition', condition }`, see [dnd/conditions.md](dnd/conditions.md), and `{ kind: 'per_turn', outcome, damageType, count, die, bonus, addModifier, edge }`, see [dnd/per-turn-damage.md](dnd/per-turn-damage.md), and `{ kind: 'defense', level, damageTypes, conditions }`, see [dnd/modifiers.md](dnd/modifiers.md), and `{ kind: 'no_healing' }` without fields, once; each sense kind and each condition once, a damage type or condition once per defense level, damage per turn may repeat); an empty list is a «Базовый» effect. It is stored as `details.components` with the `category` column always `basic`, so a server from before components reads new rows harmlessly; rows from before, with category `sense` and `{ sense, range }` in `details`, read as one sense component, broken ones as no components. An effect also has a required `duration` and a required `saveEnds` (`{ ability, edge }` or `null`, the save the bearer repeats at the start or end of each turn; no DC, it comes from whatever applied the effect), both stored in `extra` and checked by `isEffectDuration`/`isEffectSaveEnds` from `shared`; rows without them read as `{ kind: 'permanent' }` and `null`. See [dnd/durations.md](dnd/durations.md) and [dnd/attacks-and-saves.md](dnd/attacks-and-saves.md). A body of the old shape (with `category` and `details`, no `components`) is rejected with 400: the validation pipe strips unknown fields. Effects in ability step outcomes (`hit.effects`, `miss.effects`, plan [plan/done/abilities.md](plan/done/abilities.md), stage 8): the body sends `{ effectId }` (up to 5 distinct per outcome, none on a miss without a check); responses add `effect` (`name`, `isPublic`, `image`) or `null` when the effect's author hid it from the reader. They live in table `ability_step_effects` (migration `0027`: `ability_id` and `effect_id` with `ON DELETE CASCADE`, `step`, `outcome`, `position`), not in `extra.steps`. A link may point only at an effect the ability's author sees (else 400 «Эффект из применения не найден»); publishing with own hidden effects is a 409 «Сначала опубликуйте эффекты: …» unless the body has `publishEffects: true`, which publishes them in the same transaction. The author's effect card adds `abilities` (`{ mine, othersCount }`, which abilities apply it), and `hideAbilities: true` on an effect edit that unpublishes it also hides the author's published abilities that apply it. Plans: [plan/done/abilities.md](plan/done/abilities.md), [plan/done/effects.md](plan/done/effects.md).
- Monsters (`/monsters`, `monsters` module, migration `0030`): a simple catalog with the same access, images at `/monsters/:id/image`. The body has `category` (one of the 14 creature types), `statBlock` (checked by `isMonsterStatBlock` from `shared`) and `role` (`regular` | `unique`). The type is stored in the `category` column, the stat block and role in `extra`, `details` stays empty; a row with a broken stat block reads with the default one, an unknown type as `aberration`, a missing role as `regular`. See [dnd/monsters.md](dnd/monsters.md) and [plan/done/monsters-npcs.md](plan/done/monsters-npcs.md).
  - Abilities on a monster (`/monsters/:monsterId/abilities`, `monsters/abilities/`, migration `0031`): table `monster_abilities`, like `character_abilities` but with `per_day` (a spell's «N/день», `null` — at will) instead of `prepared`. Read only with the card (`GET /monsters/:id` gives `abilities`, the list doesn't), for any viewer, by the same visibility rules. Writes are author-only with the catalog's answers (`changeMonsterLinks` with `lockAuthoredEntry`: another user's published monster — 403, hidden — 404) and return the whole list: `POST` `{ abilityId, perDay? }` takes any category the author can see (otherwise 400; repeat — 409); `PATCH /:entryId` `{ perDay }` — a number 1–9 only for a spell the author can see (otherwise 400 «Частоту в день задают только заклинанию»), `null` always; `DELETE /:entryId` removes any row.
  - Gear and effects on a monster (`/monsters/:monsterId/items`, `/monsters/:monsterId/effects`, `monsters/items/`, `monsters/effects/`, migration `0032`): tables `monster_items` (an item with a `quantity` 1–9999, one row per item, no locations) and `monster_effects`, read with the card as `items` and `effects` by the same rules as a character's inventory and effects (the shared mappers are `items/item-link.ts` and `effects/effect-link.ts`). Writes as for abilities: `POST /items` `{ itemId, quantity }` — an item the author can see, a pack as one item; a repeat is 409 «Предмет уже есть в снаряжении», not a sum; `PATCH /items/:entryId` `{ quantity }`; `POST /effects` `{ effectId }` (repeat — 409 «Эффект уже наложен»); `DELETE /:entryId` on both removes any row.
- Maps (`/maps`, all behind `SessionOrApiTokenGuard` and open to a token except deleting a map, owner-only — another user's map is a 404 «Карта не найдена»). Design and plan: [plan/map.md](plan/map.md); the model itself lives in `packages/shared/src/map/`.
  - `GET/POST /maps`, `GET/PATCH/DELETE /maps/:id` — map records (`MapsService`). The list adds `startCount`, the number of start points on each map (how many players it is for). A map has a size, `width` × `depth` cells (`POST` takes them, default 32 × 32, each 1…`MAP_MAX_SIZE`); cells run from `[0, 0, 0]`, the height is shared by all maps (`MAP_MAX_HEIGHT`). Plan: [plan/map-editor.md](plan/done/map-editor.md).
  - `POST /maps/:id/ops` `{ ops: [...] }` — a batch of map operations, parsed by `parseMapOpBatch` from `shared` (same rules for REST and the future MCP) and applied by `editMap` as one undo unit: an op past the map's width or depth is a 400. The `resize` op grows or shrinks the map by side and shifts every block when it grows west, north or down, so it loads all the chunks; its changeset carries the size before and after, and undo or redo writes the size back with the blocks. `POST /maps/:id/undo`, `/redo` — journal stack; a new op clears redo. Every edit response (`MapEditResult`) includes `changes` — the applied changeset in the same packed form as the journal (`packChangeset` from `shared`), forward form for undo too; the web applies it instead of refetching. A no-op batch keeps `seq` and returns empty `changes`. All writes run in one transaction holding `SELECT … FOR UPDATE` on the map row, so concurrent writers (GM, AI) are serialized (`MapEditService`).
  - **Map objects** (start points, monsters, NPCs, containers, items on the floor; plan: [plan/done/map-objects.md](plan/done/map-objects.md)) are ops of the same journal: `placeObject`, `moveObject`, `turnObject`, `updateObject`, `removeObject`. A batch that touches objects (or resizes) loads the map's objects (`map_objects`) and the catalog rows they and the batch refer to (`loadRefs` in `maps/objects/`): monsters with size and role, items, the owner's NPCs. `editMap` gets them as `ObjectRefs` and rejects another author's hidden monster or item, someone else's NPC, an unknown id, a second unique monster and a container heavier than its look holds (sack 30 lb, barrel 120, crate 240, chest 360, a house rule in [dnd/items.md](dnd/items.md); hidden and deleted items weigh nothing; an edit that doesn't make an already overloaded container worse passes) with a 400; links already on the map are not rechecked, and undo/redo never checks them. Object ids come from the `maps.next_object_id` counter and are never reused. Starts, creatures and containers have a `facing` (containers placed before 2026-10-20 have none and read as 0). The edit response adds `createdObjectIds` and `refs` (names, images, sizes, item weights or placeholders of the touched objects); undo and redo count object conflicts in `conflicts`. Only-object batches load no chunks.
  - `GET /maps/:id/chunks` (whole map, base64 chunks + palette + `seq` + `size`, plus `objects`, `nextObjectId` and `refs` — each link resolved to a name and image, or `{ missing: 'hidden' | 'deleted' }`: the size comes with the blocks, since a resize changes both at once), `/summary`, `/slice?y=&minX=&maxX=&minZ=&maxZ=` (horizontal ASCII slice for the AI) and `/section?axis=x|z&at=&min=&max=&minY=&maxY=` (vertical ASCII section); unset ranges default to the whole map (`0…width − 1`, `0…depth − 1`) and, for a section's height, from the ground to the top block; sizes are checked before chunks load (`slice-region.ts`). `/summary` reports the `size` and `maxHeight` next to the `bounds` of what is built, and lists the objects with a label and warnings (can't stand there, inside a block, in the air, past the border, a hidden or deleted link); `/slice` lists the objects standing on that level under the grid. Reads run in one `REPEATABLE READ` read-only transaction so the palette and chunks come from the same snapshot (`MapReadService`).
  - Tables: `maps` (palette jsonb, `seq`, `width`, `depth`; migration `0035` moved every map with chunks at negative coordinates to zero by whole chunks, cleared its journal and set the size to its chunks), `map_chunks` (`bytea` via drizzle `customType`, PK `(map_id, cx, cy, cz)`), `map_ops` (journal: every entry stores the changeset that was actually applied, in forward form — undo entries too — packed as flat `[x,y,z,before,after]` arrays; object changes ride along as whole objects before and after), `map_objects` (migration `0036`: PK `(map_id, id)`, the cell as columns, the kind's fields in jsonb `fields`, catalog links without foreign keys), `maps.next_object_id`.
  - Code: an edit is `editMap` from `shared` on chunks and objects loaded into memory (`maps/edit-run.ts`: `runOps` applies a batch, `runReplay` rolls a journal entry back, `saveEdit` checks the chunk limit and writes the dirty chunks and changed objects). Where they live is an `EditStorage` (`maps/storage/`): the chunk and object queries are written once over a table description, since `map_chunks`/`map_objects` and the scene tables have the same shape; `mapStorage(mapId)` here, `sceneStorage(sceneId)` for a game scene. The journal is separate: `map-journal.ts` writes `map_ops` and the `maps` row.
  - Limits from env (`MapLimitsConfig`, defaults in `.env.example`): `MAP_MAX_OP_VOLUME`, `MAP_MAX_BATCH_VOLUME`, `MAP_MAX_OPS_PER_BATCH`, `MAP_MAX_SIZE` (largest map width and depth, 256), `MAP_MAX_HEIGHT` (levels, 64), `MAP_MAX_CHUNKS`, `MAP_MAX_OBJECTS` (objects per map, 500). The chunk limit is checked only when an edit grows the map. Coordinates start at zero: `parseMapOp` rejects negative ones and anything past `MAP_MAX_SIZE` or `MAP_MAX_HEIGHT`, and `editMap` checks the map's own width and depth.
- Games (`/games`, `AuthGuard` only — closed to API tokens, people play, not the model; `games` module, migrations `0038`–`0043`). Plan: [plan/game.md](plan/game.md), stages 1–6.
  - Tables: `games` (`master_id`, `name`, `seat_count` 1–8, `password_hash` — bcrypt or `null` for an open game) and `game_members` (key `game_id` + `user_id`). A member is someone who entered the lobby; a seat is a member with `character_id` set (`seated_at` orders the seats). `character_id` is unique across all games — a character plays in one game, since the game will write to its sheet — and `ON DELETE SET NULL`: a deleted character frees its seat, the player stays in the lobby. The GM is never a member.
  - `GET /games` — every game for every signed-in user, the viewer's own first (GM or member), then newest first: `GameListItem` with `master`, `seatCount`, `takenSeats`, `hasPassword` and the viewer's `role` (`master`, `player`, `member` or `null`). The hash never leaves the server.

An open lobby is visible to anyone signed in; a closed one only to the GM and members, others get 403 «Игра закрыта паролем» and the page asks for the password. `POST /games` `{ name, seatCount, password? }` (an empty password = open) returns it; `DELETE /games/:id` is the GM's (else 403), members go with it.
  - `POST /games/:id/enter` `{ password? }` — enter the lobby once (403 «Неверный пароль игры»; throttler 10/min against guessing). Later visits need no password.
  - `POST /games/:id/seats` `{ characterId, allowHandover? }` — take a seat with an own player character: someone else's is 404, an NPC 400, the GM 409, already seated 409, a character in another game 409 «Персонаж уже в игре «…»», no free seat 409. The count and the insert run under `SELECT … FOR UPDATE` on the game row, so two players can't both take the last seat; a race on the same character in two games hits the unique index (409). In an open game this also makes the user a member.
  - `PATCH /games/:id/seats/me` `{ allowHandover }` and `DELETE /games/:id/seats/me` (free the seat, stay in the lobby) — 404 without a seat. `DELETE /games/:id/members/:userId` — leave (self) or remove a player (GM only, else 403); the seat and the lobby access go together, so a closed game asks for the password again. The GM can't leave their own game (409).
  - **The game log** (`game_events`, key `game_id` + `seq`): every change to a game writes an entry in the same transaction (`games/game-journal.ts`: `lockGame`, `appendGameEvent`). Each write path takes `SELECT … FOR UPDATE` on the game row first, so the lock order is always game → members → character; `appendGameEvent` bumps `games.event_seq` with `UPDATE … RETURNING`, which gives gapless numbers in order (the socket will catch up by them). An entry holds `kind`, `actor_id` (`ON DELETE SET NULL`), `as_kind`/`as_id` (on whose behalf: `master`, later a character or a monster; no FK, so the entry outlives them), `scene_id` (FK to `game_scenes`, `ON DELETE SET NULL`; set on scene events), `intent` and `result` jsonb shaped by `GameEventPayloads` in `shared`, `changes` jsonb (migration `0043`; only a scene edit's changeset, left out of what the GM reads — `game-event-read.ts` selects the columns by name — since it can be large and only undo and the broadcast need it), with names snapshotted (a character's name stays readable after it is deleted). Kinds so far: `game.created`, `session.started`, `session.ended`, `library.refreshed`, `scene.created`, `scene.activated`, `scene.restarted`, `scene.opened`, `scene.closed`, `scene.edited`, `scene.undone`, `scene.redone`, `figures.placed`, `figure.moved`, `figure.placed`, `figures.round`, `figure.refreshed`, `figure.dashed`, `member.entered` (only when the insert added a row: a repeat or a concurrent double enter logs nothing), `seat.taken` (in an open game it also makes the player a member, with no `member.entered` before it), `seat.updated`, `seat.freed` (`reason: freed | character_deleted`), `member.left`, `member.removed`. Not logged: a wrong password (it changes nothing, and anyone could flood the log) and the password itself, ever (`hasPassword` only). Deleting a character frees its seat explicitly with an entry (`games/release-character-seat.ts`, called from `CharactersService.remove` in its transaction before the delete). Deleting a game takes its log with it by cascade, with no «deleted» entry.

  - **The locked sheet** (`games/sheet-lock.ts`): while a character is seated in a game with a running session, every write to its sheet answers 409 «Персонаж в игре «…»: идёт встреча, лист закрыт до её конца» — `PUT`/`PATCH`/`DELETE /characters/:id` (spell slots included), inventory (add, change, move, remove), abilities and effects on the character. `assertSheetUnlocked` runs after the owner check (another user still gets 404) and, in `CharactersService.remove`, before `releaseCharacterSeat` (which would free the seat first). Images and link access are not the sheet and stay open. There is no flag: the lock is derived from the seat and the session, so ending the session, freeing the seat or removing the player unlocks it.       - `PUT /games/:id/figures/:characterId` `{ at }` (200) — the GM only (403 «Ставить фигурки и менять их запас движения может только мастер»): any cell inside the scene where a Medium figure can stand and no creature is, hidden ones included (409 «Здесь фигурке не встать…»); no path, no allowance spent. It also puts an unplaced seated character on the scene (a new row facing south). Writes `figure.placed` (`from` null for a new one).
      - `POST /games/:id/figures/round` — «Новый раунд»: every figure's `moved` and `dashes` back to 0, `figures.round { scene, count }`; `POST …/:characterId/refresh` — one figure's (`figure.refreshed`); `POST …/:characterId/dash` — «Рывок», `dashes` + 1 (`figure.dashed { dashes }`). GM only. A cell that isn't three integers is 400.
    - `GET /games/:id/figures/:characterId/image` — the main image's thumbnail for anyone who sees the figure (the GM; members while the scene is open), even when the character's own gallery is private: at the table everyone sees the token. No figure or no image 404; cached forever on success only, like the scene images (the client puts the image id and version in the query).
- Bookmarks (`/bookmarks`, `AuthGuard`, `bookmarks` module, migration `0028`; monsters added in `0033`). Plan: [plan/done/bookmarks.md](plan/done/bookmarks.md), monsters — [plan/done/monsters-npcs.md](plan/done/monsters-npcs.md), stage 7.
  - Table `bookmarks`: `user_id` and five nullable links `character_id`, `item_id`, `ability_id`, `effect_id`, `monster_id`, each `ON DELETE CASCADE` (a deleted target leaves the bookmarks by itself); check `bookmarks_one_target` — exactly one link is set; unique `(user_id, <link>)` per link.
  - `GET /bookmarks` — the caller's bookmarks, newest first, in one query (`loadBookmarks`): the target's visibility is checked in the join, by the same rules as its own page (`characterVisibleTo`, `entryVisibleTo`). A target hidden from the caller comes as `target: null` with only `kind` and `targetId`.
  - `GET /bookmarks/:kind/:targetId` → `{ bookmarked }`; `PUT` adds (only a target the caller sees now, else 404 «Не найдено»; a repeat is a no-op, not 409); `DELETE` → 204 removes the caller's own row without checking the target, so a bookmark on a hidden target can still be removed. `kind` is one of `BOOKMARK_KINDS` from `shared` (else 400), `targetId` a UUID (else 400).
- CORS with `credentials: true` for `FRONTEND_URL` (default `http://localhost:5173`) — needed only in dev, where web and API run on different ports.

## Auth

- JWT access + refresh tokens in `httpOnly`, `sameSite: lax` cookies (`access_token`, `refresh_token`; `secure` in production). Secrets/TTLs from `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_EXPIRES_SEC` (default 15 min), `JWT_REFRESH_EXPIRES_SEC` (default 30 days).
- **API tokens** (`api-tokens` module) are for external clients — the MCP servers through which an AI works with the app (plan [plan/ai-access.md](plan/ai-access.md)). Format `dnd_<random>`, only the sha256 hash and a display prefix are stored. `SessionOrApiTokenGuard` accepts either the cookie session or `Authorization: Bearer dnd_…` (with the header present it never falls back to the cookie). A token passes only into handlers marked `@AllowApiToken()` (`api-tokens/allow-api-token.decorator.ts`, method-level only, so a new route stays closed until opened on purpose); an unmarked handler answers 403 «Через API-токен это сделать нельзя — сделайте это в интерфейсе». Open to a token: reading, creating and editing characters (not `PUT /characters/:id/access`), their images (not deleting one), inventory, abilities and effects (removing a link included), the item, ability, effect and monster catalogs with their images (not deleting an entry or its image), the monster's abilities, items and effects, the maps (not `DELETE /maps/:id`) and `GET /map-catalog?kind=monster|item|npc&q=` (search of what can be placed on a map: own and published monsters with size and role, items with category and weight, own NPCs, 20 at most; `MapCatalogService`). A token doesn't change visibility either: `keepPublicationForToken` (`catalog/token-publication.ts`) makes a catalog `POST` by token 403 unless `isPublic: false`, a `PUT` 403 unless `isPublic` equals the stored value, and any of `publishContents`, `hidePacks`, `publishEffects`, `hideAbilities` 403. Routes still behind the cookie-only `AuthGuard` — `/api-tokens` (a leaked token can't mint new ones), the profile and settings, `/auth/*`, bookmarks — answer a token with 401.
- `users.password_hash` is nullable: an account created by signing in through lolka has no password until its owner sets one, and `login` refuses it with the same `Invalid login or password` 401 as a wrong password. External sign-in identities live in `user_identities` (`provider` + `subject`, unique both ways); plan in [plan/done/lolka-login.md](plan/done/lolka-login.md).
- **Sign-in through lolka** (OAuth 2.0 Authorization Code + PKCE S256, `auth/lolka/`). Both routes are full browser navigations that always answer with a redirect:
  - `GET /auth/lolka/start` puts `state`, `code_verifier` and the optional `?next=` return path (checked by `safeReturnPath` from `shared`, dropped if unsafe) into a 10-minute `httpOnly` cookie `lolka_oauth` (path `/api/auth/lolka`, `sameSite: lax`, so it survives the top-level GET back from lolka) and redirects to lolka's `/oauth/authorize`.
  - `GET /auth/lolka/callback` takes and clears that cookie, checks `state`, exchanges the code (`LolkaOAuthService`: server-side, 10 s timeout, lolka's token is used once for `/oauth/userinfo` and never stored), finds or creates the user (`UserIdentitiesService.findOrCreateUser`), sets our usual cookies and redirects to the saved return path or `/`. Any failure redirects to `/login?lolkaError=denied|state|failed|rate_limited`, keeping `&next=` so the second try still returns there.
  - A new account gets the lolka nickname (only at creation), a technical login `lolka_<8 hex>` and no password.
  - Config: `LOLKA_CLIENT_ID`, `LOLKA_CLIENT_SECRET`, `LOLKA_REDIRECT_URI`, optional `LOLKA_BASE_URL`. Without `LOLKA_CLIENT_ID` the feature is off: the routes are 404 and `GET /auth/providers` (public) answers `{ lolka: false }`, which is what the web uses to show the button.
  - `UserIdentitiesService` is provider-agnostic: another external sign-in only needs its own routes and a different `provider`.
- Refresh tokens carry a random `jti` and are stored in the DB only as a sha256 hash (`RefreshTokenService`); refresh rotates the token.
- `AuthGuard` reads the access cookie and puts the payload on `request.user`.

## Security middleware

- `configure-app.ts` (called from `main.ts` and from the integration tests) sets `trust proxy = 1` — exactly one proxy (edge-nginx) appends the client IP to `X-Forwarded-For`. Changing the proxy chain means changing this number, otherwise rate limiting sees the wrong IP.
- `helmet()` with its default CSP — fine while scripts stay same-origin. Google Fonts and Mantine's runtime `<style>` tags are covered by the defaults (`https:` / `'unsafe-inline'` in `style-src`/`font-src`). A new third-party script/connect origin means extending the CSP directives there. `img-src` additionally allows `blob:`: character images are fetched as blobs and shown through object URLs. The Vite dev server sends no CSP, so a CSP mistake only shows on the built server. `upgrade-insecure-requests` is production-only.
- `AuthController` is guarded by `@nestjs/throttler` (registered in `AuthModule`, in-memory storage): 60/min default, `login` 10/min, `register` 5/hour, per IP. `LolkaController` has its own 20/min. The 429 message is in Russian because the web UI shows the server's `message` as-is.

## Tests

Vitest (`vitest.config.ts`, `vitest.config.e2e.ts`) with `unplugin-swc` — Vitest's default esbuild transform can't emit decorator metadata, without which Nest DI can't resolve constructor params.

- Unit tests: `*.spec.ts` next to the source.
- Integration tests (plan: [plan/done/testing.md](plan/done/testing.md)): `test/*.e2e-spec.ts`, run with `pnpm --filter api test:e2e`. Each file boots the full `AppModule` through `createTestApp()` (`test/support/test-app.ts`) with the same setup as production (`src/configure-app.ts`: `/api` prefix, cookies, validation) and calls it with supertest; `loginAs(login)` registers a user and returns an agent that keeps its cookies.
  - **Database:** only `TEST_DATABASE_URL`, never `DATABASE_URL` (which points at production). The name must end in `_test`, checked before the run and again on the live connection; otherwise nothing runs. Locally it is `dnd_online_test` on the production Postgres server (created 2026-10-15), through the same tunnel.
  - `globalSetup` applies the migrations from `drizzle/`; every test file truncates all tables first, so files run one at a time (`fileParallelism: false`).
  - Catalogs share one scenario, `describeCatalog` (`test/support/catalog-scenario/`): access to hidden and published entries, the image and access by API token; each catalog's own fields are tested in its file.
  - The `test-runner` subagent (`.claude/agents/test-runner.md`) runs all checks, e2e included, and reports without changing anything.
  - The `ThrottlerGuard` is replaced by a pass-through; request logs are off (`LOG_LEVEL=debug` brings them back).
- Globals are off: import `describe`/`it`/`expect`/`vi` from `vitest`.
- `pnpm test` type-checks first (`tsc -p tsconfig.json --noEmit`, which covers the specs). Vitest strips types without checking them, and `nest build` excludes the specs, so without this step broken test types went unnoticed.
- Drizzle's `const [row] = await …select()` is typed as the row, not `row | undefined` (`noUncheckedIndexedAccess` is off). A function that returns such a lookup gets an explicit `Promise<Row | undefined>` return type, so callers have to handle "not found".
- Single test: `pnpm --filter api exec vitest run path/to/file.spec.ts` (or `-t "test name"`).
