# Интеграционные тесты API

Живой документ: решения, открытые вопросы и чеклист этапов. Отмечаем сделанное по ходу работы (`[x]`). Составлен 2026-10-15.

## Зачем

Сейчас API проверяется двумя способами:

- **unit-тесты** (`*.spec.ts`) — проверяют функции и DTO по отдельности, база в них подменена;
- **скрипт Claude** — `check-catalog.mjs` во временной папке сессии: входит под двумя тестовыми аккаунтами и гоняет запросы к живому серверу на прод-базе. Работает, но он не в репозитории, запустить его может только Claude, а записи создаются в прод-базе.

Интеграционные тесты закрывают этот промежуток: поднимают весь сервер (`AppModule`) с настоящим Postgres и проверяют его запросами, как клиент. Ловят то, чего не видят unit-тесты:

- **права доступа** — скрытая запись не видна чужому, опубликованную нельзя менять не автору. Ошибка здесь — утечка чужих данных, и это самое опасное место;
- **работу с настоящей базой** — jsonb, каскадное удаление, уникальность, миграции;
- **поломки при обобщении кода** — каталоги предметов, способностей и эффектов делят общий код (`catalog/`), правка ради одного может сломать другой.

Браузерную проверку они не заменяют: интерфейс по-прежнему смотрим глазами (план браузерных тестов — потом, отдельно).

## Принятые решения

- **Отдельная тестовая база `dnd_online_test`** на том же сервере Postgres, что и прод (решено с пользователем 2026-10-15). Локально — через тот же туннель (`localhost:5433`), что и основная база.
- **Адрес тестовой базы — своя переменная `TEST_DATABASE_URL`**, а не `DATABASE_URL`. В `.env` `DATABASE_URL` указывает на прод, и тесты не должны взять его по ошибке.
- **Защита от прода.** Перед запуском тесты проверяют, что имя базы в `TEST_DATABASE_URL` оканчивается на `_test`, иначе падают сразу, ничего не тронув. Тесты очищают таблицы, и прогон по прод-базе стёр бы данные.
- **Перед прогоном — миграции** (`drizzle-kit migrate` в `globalSetup` Vitest). Тестовая база всегда в схеме текущего кода, вручную её не готовим.
- **Чистая база на каждый файл тестов**: в начале файла таблицы очищаются (`TRUNCATE … CASCADE`). Файлы идут по очереди, не параллельно — база одна.
- **Приложение собирается так же, как в `main.ts`**: префикс `/api`, `cookie-parser`, `ValidationPipe`. Эту настройку выносим из `main.ts` в общую функцию, чтобы тест не разошёлся с продом.
- **Ограничение частоты входа в тестах выключено** (подмена `ThrottlerGuard`), кроме теста, который проверяет само ограничение.
- **Пользователи — через API**: регистрация и вход, как у настоящего клиента. Помощник `loginAs(name)` возвращает агента supertest с куками.
- **В CI — свой Postgres**: в GitHub Actions задача `test` поднимает Postgres как service-контейнер и гоняет unit-тесты, линтер и интеграционные. Деплой ждёт её (`needs: test`): если тесты упали, на прод ничего не уходит. Серверная тестовая база для CI не нужна.
- **Тесты — рядом с остальными e2e**: `apps/server/test/*.e2e-spec.ts`, команда `pnpm --filter api test:e2e` (уже есть). Заготовку `app.e2e-spec.ts` («Hello World») заменяем.

## Агент для прогона

`.claude/agents/test-runner.md` — субагент Claude Code: гоняет сборку `shared`, `pnpm test`, линтер, формат и `test:e2e`, ничего не меняет и возвращает короткий отчёт (что прошло, что упало и почему). Claude запускает его в фоне после правок, перед коммитом или деплоем. Обходить проверку `_test` ему запрещено; недоступный туннель он отмечает как «e2e не прогнаны», а не как падение.

## Открытые вопросы

- **Версия Postgres в CI** — 17, как на сервере (17.10, узнали на этапе 1).
- **Скорость.** Если прогон станет долгим, очищать только таблицы, которые тест трогал, или заворачивать тест в транзакцию.
- **Браузерные тесты** (Playwright Test: сценарии в браузере, обе схемы, 390 px, сравнение скриншотов) — отдельный план, после этого.
