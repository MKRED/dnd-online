# Web (`apps/web`)

Vite + React 19 + TypeScript, Mantine 9.7 (UI, light «parchment» scheme by default, dark «charcoal + brass» via the header toggle), react-router 7, three.js + react-three-fiber 9 + drei for the 3D map, `@tabler/icons-react` for icons (the set Mantine suggests; only imported icons end up in the bundle).

## Layout

- `src/main.tsx` — providers: `MantineProvider(theme, cssVariablesResolver)` → `AuthProvider` → `RouterProvider`.
- `src/router.tsx` — routes. Everything except `/login` and `/register` sits behind `RequireAuth`; those two behind `RequireGuest`. `RequireAuth` sends a guest to `/login?next=<the page>` (`features/auth/returnPath.ts`), so a shared character link opens again after signing in. The login and register pages keep `?next=` in the links between them and in the lolka button, and after success go to it; `RequireGuest` redirects a signed-in user there too. Only same-site paths count (`safeReturnPath` in `shared`), so `?next=` can't send anyone to another site.
- `src/features/<feature>/` — non-page logic and feature UI (API client, context, validation, labels, shared forms), public surface via `index.ts`. Currently `auth`, `characters`, `abilityLinks`, `catalog`, `items`, `simpleCatalog`, `monsters`, `maps`, `apiTokens`, `profile`. Shared helpers live in `src/lib/`, among them the image bytes cache: `imageUrlCache.ts` loads an image through `fetch` once and revokes its object URL 15 s after the last component stops showing it, keyed by the image's API path (variant and version included); `useImageUrls`/`useImageUrl` are the hooks over it. Character and catalog images (items, abilities, effects) all go through it.
  - `characters/CharacterForm/` — the character-sheet form (uncontrolled `useForm`, sections memoized via `formErrorsEqual` from `src/components/form/`), used by both the create and edit pages. `initialValues` are read once on mount, so the edit page mounts it only after the character has loaded. `characterFormValues.ts` maps form values ↔ API payload (`toCreatePayload`, `fromCharacter`). The form is long and its submit button sits at the bottom, so a failed submit must not leave errors only next to fields far above: the form has `noValidate` (no browser bubbles, every check goes through `useForm`), the failure handler scrolls the first invalid field to the middle of the screen and focuses it (`focusField`, by Mantine's `data-path`), and `FormErrorSummary` above the button lists the errors in page order (`formErrorFields.ts`, built on `collectErrorFields`), each name a link to its field. These pieces live in `src/components/form/` and the monster form uses them too. The server error is shown there too.
  - `characters/CharacterGallery/` — the character's image gallery on the edit page (plan: [plan/done/character-images.md](plan/done/character-images.md)). It sits outside the sheet `<form>` and saves every change at once. `useCharacterImages` holds the data and the edits; `GalleryTile` and `UploadTile` (`@mantine/dropzone`) make the grid; `GalleryLightbox` (`@mantine/lightbox`) and `ThumbnailEditor` (`react-easy-crop`) are mounted only while open. If the phone page is pinch-zoomed, the stock `position: fixed; inset: 0` viewer would open zoomed and shifted with its toolbar off screen, so `useZoomedViewport` places it over the visible part of the page (`visualViewport`) and scales it back; at scale 1 it changes nothing. Image bytes come through the `lib/imageUrlCache.ts` cache; `characterImagePath` builds their paths. `CharacterAvatar` is the main image's thumbnail (a rounded square) with initials as the fallback. Tests stub `URL.createObjectURL`, which jsdom lacks.
  - Characters and NPCs (plan: [plan/done/monsters-npcs.md](plan/done/monsters-npcs.md), stage 8): the list (`pages/CharactersPage/`) has the «Игровые» / «НПС» chips with counts, the chosen one in the URL (`?kind=npc`, `characterKinds.ts`; none or anything else means player characters), and its create button opens `/characters/new?kind=npc` («Создать НПС»), which seeds the form's type. The form's «Основное» starts with the «Тип» switch (`SegmentedControl`), so the type can still be changed. The sheet header marks an NPC with an «НПС» badge before the classes; the sheet's «← К персонажам» and deleting return to the character's own chip.
  - `characters/SheetLockAlert.tsx` — «Лист закрыт» with a link to the game when `character.sheetLock` is set (the character is seated in a game with a running session). The view page then hides «Редактировать», the «Ещё действия» menu and every in-sheet edit (it passes no change callbacks, as for a viewer by link), keeping «Поделиться»; the edit page shows the alert instead of the form and keeps the gallery.
  - `characters/ShareDialog.tsx` — «Доступ к персонажу» from the sheet's «Поделиться»: «Только я» or «Все, у кого есть ссылка», saved at once (`PUT /characters/:id/access`), with the sheet's address and a copy button. A shared character gets «По ссылке» in the list and a reminder line on its sheet.
  - `characters/CharacterSheet/` — the read-only character sheet on `/characters/:id`, the same for the author and for someone who opened it by link (plan: [plan/done/character-sharing.md](plan/done/character-sharing.md)). Sections follow the form's order and an empty one is not shown; derived numbers (modifiers, initiative, save and skill bonuses) use the form's `abilityMath.ts`, and both group skills through `skillsByAbility.ts`. `SheetImages` shows the main image and a strip of the others and reuses the gallery's `useCharacterImages` and `GalleryLightbox`. The old text fields for attacks, known spells and features are not on the sheet: catalog abilities replace them. The page passes its own `aside`: the author's buttons, or «Автор: … · только просмотр». The inventory, the applied effects, the abilities and the spent spell slots are edited on the sheet itself (the page passes `onInventoryChange`, `onEffectsChange`, `onAbilitiesChange` and `onSpellSlotsChange` only to the author).
  - `abilityLinks/` — catalog abilities on a creature, shared by the character sheet and the monster card. `AbilityRow` links the name to the card and adds a short summary (`abilitySummary`: a skill repeats only what its group title lacks — the reaction trigger, the casting time, a legendary action's cost above 1 — plus the recharge and costs; a spell skips the slot) with slots for the owner's own controls (`leading`, `trailing`). `SkillsBlock` is the «Умения» fieldset: groups, «+ Способность» and `AddAbilityDialog` (own and catalog abilities, the circle next to a spell's name, added ones disabled; a character isn't offered «Монстра» abilities, a monster gets them first and a «В день» select for a spell, `PerDaySelect`); the dialog stays open after adding, since abilities come in batches. Edits go through `useAbilityLinksEditor` (one at a time, removal without confirmation, the error under the rows so nothing moves under the pointer) and `abilityLinksApi(base)`.
  - `characters/Abilities/` — the «Умения» and «Заклинания» blocks of the sheet (plan: [plan/done/character-abilities.md](plan/done/character-abilities.md)), after the ability scores, built on `abilityLinks/`. `abilitiesView.ts` groups the rows: «Умения» (non-spells) by activation in `ABILITY_ACTIVATION_KINDS` order with hidden and deleted rows last as «Недоступны»; «Заклинания» as «Заговоры», then circles 1–9, a circle shown if it has spells or slots. A spell of circle 1+ (`canBePrepared`) gets the «подготовлено» dot (`PreparedMark`), a toggle for the author.
  - Spell slots: the form's «Ячейки заклинаний» (`CharacterForm/SpellSlotsSection.tsx`) sets how many slots each circle has; `spellSlotsFormValues.ts` keeps the spent ones from the loaded character and cuts them down to the new count, so saving the form doesn't reset them. On the sheet `SpellSlotPips` draws a circle's slots as dots in the circle header (full — left, spent — empty), and the author clicks a full one to spend a slot or an empty one to get it back; each click is a `PATCH /characters/:id` with `spellSlotsExpended`, one at a time (`useSpellSlotsEditor`). «Долгий отдых» sits in the first circle with slots and keeps its place while hidden (nothing spent), so appearing after the first spend doesn't move the dots under the pointer.
  - `characters/Inventory/` — the inventory block of the sheet (plan: [plan/done/character-inventory.md](plan/done/character-inventory.md)): «При себе» with the load against Strength × 15 (`LoadSummary`, red over capacity, never blocking), a collapsed «Хранилище» below and the money line. A row has the thumbnail, the name linking to the item card, the quantity and the row weight (on a narrow screen these go under the name), ⇄ to move it to the other place (a stack asks «Сколько?», default all) and a ⋯ menu with «Изменить количество» and «Убрать из инвентаря» (confirmed). A hidden or deleted item is a grey row with only «Убрать»; an item hidden from the owner that its author sees on the shared sheet keeps its card with a «Не действует» badge and is left out of the load. «+ Добавить предмет» opens `AddItemDialog` (search over own items and the catalog, quantity, place), which stays open after adding, since an inventory is usually filled several items in a row. For a pack it asks «Целиком» or «Распаковать» (`PackChoice`, default unpack) with the row count and weight of both, and says how many hidden contained items will be left out. Every change goes through `useInventoryEditor` (one request at a time, the server's message shown above the list) and replaces the whole inventory with the server's answer.
  - `items/` — the items catalog (plan: [plan/done/items.md](plan/done/items.md)). Pages: `/items` (tabs «Мои»/«Каталог» kept in `?tab=`, grid or list remembered in `localStorage`; filters above the list — category chips, name search, rarity, sorting — run in the browser over the loaded tab and live in the URL, `?cat=&rarity=&q=&sort=`, changed with `replace`; plan: [plan/done/items-filters.md](plan/done/items-filters.md), code: `ItemFilters/`), `/items/:id` (the card everyone sees; the author gets «Редактировать» and «Удалить»), `/items/new` and `/items/:id/edit` (the edit page redirects a non-author to the card). Equipment packs (plan: [plan/done/item-packs.md](plan/done/item-packs.md)):
    - Form: the «Состав» block is `ItemForm/PackContentsField/`. Its candidates are the same `mine` and `catalog` lists, filtered in the browser (no packs, not the item itself), and the search text is controlled so it clears after a pick. The weight hint sums the visible rows.
    - Saving: `saveConfirmation` decides whether to ask first, and `SaveConfirm` shows the question by the form buttons. It asks before publishing a pack with own hidden items (sets `publishContents`) and before hiding an item that lies in public packs (`hidePacks`) or in other users' characters' inventories (there it stops acting on the character).
    - Card: `PackContents/PackContentsView` lists the contents.
    - Delete: the confirmation names the packs and the characters carrying the item (`deleteConfirmText`); other users' are a count.
    - `ItemForm/` — the item fields; the image field and its save are the shared ones from `catalog/` (below). `saveItem.ts` saves the item, then its image, through `saveWithImage`.
    - `ItemThumb.tsx` and `ItemCollection/` wrap the shared thumbnail and grid/list with the item image paths, weight and cost; `ItemDetails` is the card.
  - `catalog/` — what the item, ability and effect catalogs share (plan: [plan/done/abilities-effects.md](plan/done/abilities-effects.md)). Each catalog section has its own item under «Справочник» in the side panel; `CatalogListLayout` puts the «Справочник» title, the create button, the section tabs (`CatalogNav`: «Предметы · Способности · Эффекты», each a route; Mantine tabs are buttons, so a tab navigates) and the «Мои»/«Каталог» (`useCatalogScope`, `?tab=`) and grid/list (`useCollectionView`, one `localStorage` key for the whole reference) switches above a section's list. Also here:
    - `catalogApi(base)` — the CRUD and image requests of a catalog under its path, and `imagePath` for the image bytes cache; `useCatalogList` and `useCatalogEntry` load a tab or one entry (both expect a stable loader and texts, or the effect reloads).
    - `ImageField/` — the image and its thumbnail in a form, saved with the form's button. `imageDraft.ts` holds the image state until then (none, saved with a possibly changed crop, or a new file with its natural size); `saveWithImage` saves the entry first, then uploads, re-cuts or deletes the image. A crop picked on a new file is in its natural pixels and is rescaled by `full.width / naturalWidth` after the upload. If the image fails after the entry is saved, the form stays open with the error and the next save updates that entry rather than creating another. `ThumbEditor` is `react-easy-crop` with `restrictPosition={false}` and a `minZoom` below 1, so the image can sit inside the frame with transparent margins; `objectFit="cover"` makes the frame as tall as the stage (with the default `contain` a long sword got a frame the height of the sword). The crop is checked with `catalogThumbCropError` from `shared`, the same rule the server uses.
    - `CatalogThumb/` — the server thumbnail on a neutral square (its margins are transparent) with the first letter as the fallback; `CropPreview` shows an unsaved crop by positioning the image inside the square. `EntryImage` is the full image on a card, `DetailsField` a label/value row.
    - `CatalogCollection/` — the grid and the list, with the badges and optional numbers (an item's weight and cost) given by the section; `SearchField` — the name search with the «/» hotkey; `catalogSearch.ts` — the «ё = е» case-insensitive match and the name collator.
  - `simpleCatalog/` — the ability and effect sections (plans: [plan/done/abilities.md](plan/done/abilities.md), [plan/done/effects.md](plan/done/effects.md)). Both are one set of pages driven by a `SimpleCatalogDef` (`ABILITIES`, `EFFECTS` in `simpleCatalogs.ts`: path, API, the ability categories, the entry kinds for chips and badges — an ability's category, an effect's component kinds or «Базовый» without them — Russian texts in the right gender), routed under `/abilities` and `/effects` with a `key` per section so React doesn't carry one section's state into the other. The list has the name search and «Сначала новые»/«По названию» in the URL (`?q=&sort=`, `simpleFilters.ts`); kind chips (`?cat=`, `CategoryChips`) show when a section has more than one kind, and an effect with several component kinds counts in each. The form: image, name, the ability category select (abilities only), the section's own fields from `def.extras` (`catalogExtras.tsx`: the form component, its part of the request body, the card rows and the list value): for effects `EffectFields/` — the components as a list of cards with a ✕ and a «+ Составляющая» menu of kinds (values in `effectForm.ts` with the per-kind conversion in `componentValues.ts` and the field rules in `componentRules.ts`, list rows keyed by a random id, each row validated on its own and only by its kind's rules, a repeated sense or condition marked on the later row, the card's fields picked by kind from `KIND_FIELDS` in `ComponentsField`, a field-less kind disabled in the menu once the effect has it; damage per turn and defenses keep their fields in nested `perTurn` and `defense` objects with their values and rules in `perTurnForm.ts` and `defenseForm.ts`), the duration (`DurationField`, a kind select plus that kind's fields, and a line showing how the card will read it) and «Снимается спасброском» (a checkbox opening the ability and start/end of turn); for abilities the activation and costs (`UsageField`: the activation kind with its condition or time, and a checkbox per cost that opens its fields), description, «Показывать в каталоге». The card shows these fields in full, the list in short (the duration of an effect, the activation of an ability). `def.extras` may also give `saveConfirmation` — a question before saving, shown by `SaveConfirm/` at the form buttons, whose answer adds flags to the request (publishing an ability with own hidden effects in its steps sets `publishEffects`; hiding an effect that public abilities apply offers `hideAbilities`) — and `Guide`, the «?» button next to the form title (`AbilityGuide/`, abilities only). The ability step outcomes pick catalog effects (`StepsField/EffectRows.tsx`; both effect lists load once per form in `useEffectCandidates`), the card shows them as links (`StepEffectsLine`), and deleting an effect names the abilities that apply it (`deleteConfirmText.ts`).
  - `monsters/` — the monster section (plan: [plan/done/monsters-npcs.md](plan/done/monsters-npcs.md)), its own pages rather than `simpleCatalog`, built from the shared catalog pieces. The list (`MonsterList/`) has the name search, type chips (`CategoryChips` with `hideEmpty`: only the types present, plus the chosen ones), a CR range «от–до» and the sort, all in the URL (`?q=&cat=&cr_min=&cr_max=&sort=`, `monsterFilters.ts`). The form (`MonsterForm/`) is grouped like the character form, uncontrolled with memoized sections and the same error summary; `validateMonsterForm` repeats every server limit, because the server answers any stat-block error with one generic message. `monsterFormValues.ts` maps the stat block ↔ form values (empty optional numbers ↔ `null`). The card (`MonsterCard/`) is laid out like the character sheet and reuses its `StatTile` and `SheetField`. Its abilities (`Abilities/`, on `abilityLinks/`) are edited on the card by the author: «Умения» in the stat block's sections (Черты, Действия, Бонусные действия, Реакции, Легендарные действия with the per-round count in the title; `monsterAbilitiesView.ts` maps every activation to one of them) and «Заклинания» by frequency («Неограниченно», then «N/день» descending) under the «Колдовство» line, each row with its circle and, for the author, a frequency select. The legendary count and spellcasting move from «Защита, чувства, языки» into those titles once their groups exist. The top of the card (`MonsterTop`) has the effects strip (`EffectLinksStrip` from `characters/Effects/`, which takes the rows, the owner's API path and «на персонажа»/«на монстра» for the hints), the «С эффектами / Без эффектов» switch and `EffectSummary`; AC and speeds are the totals (`monsterTotals.ts` on `creatureTotals` from `shared`), and `speedTile` gets the stat block's own special speeds so they don't count as a change. «Снаряжение» (`Gear/`) is one list with quantities: a row with the thumbnail, link and ×N, the author's menu (quantity via `QuantityDialog`, remove) and «+ Предмет» (`AddGearDialog`, already added items disabled).
  - `games/` — games (plan: [plan/game.md](plan/game.md), stages 1–5): `gamesApi.ts`, `gameScenesApi.ts` (the scene routes, `scenePagePath`, and `sceneObjectImages(gameId)` — the object thumbnails from the game library's copies), the labels (`seatsLabel`, `ROLE_LABELS`) `gameSocket.ts` (one Socket.IO connection per page, opened by the first lobby and closed by the last; an `unauthorized` refusal refreshes the session once per 10 s and reconnects), `useGameRoom(gameId, handlers, since?)` (joins the room — the first time from `since`, the `GameDetail.eventSeq` the page loaded at, so what happened between the load and the join comes as `onResync` — rejoins with `afterSeq` after a drop, returns `online`; handlers `onChanged`, `onEvent`, `onResync`, `onClosed` — one room hook per page, since a second one's leave would take the whole socket out of the room) and `gameEventText.ts` (a log entry as an impersonal Russian line — the author's gender can't be told from a nickname — and its time). Pages:
    - `pages/GamesPage/` (`/games`, «Игры», first in the side panel) — the shared list (`GameCard`: name, a lock for a closed game, the GM, «Места: n из m», the viewer's role, «Идёт встреча» on its own line so the name keeps its room on a phone), «Создать игру» opens `CreateGameModal` (name, seats 1–8, password — empty is open) and goes to the new lobby.
    - `pages/GameLobbyPage/` (`/games/:id`) — `GameLobbyPage` loads the game; a 403 means a closed lobby not entered yet, and `LobbyPassword` asks for the password once. `LobbyView` shows the GM, the seats in a grid (`SeatCard` for a taken one: character, species and classes, player, whether control can be handed over — a switch on the viewer's own seat; `FreeSeatCard` dashed, with «Занять» for whoever can sit) and the role's actions: «Освободить место», «Выйти из игры», the GM's «Убрать из игры» and «Удалить игру», each confirmed. The lobby is live: `LobbyView` re-reads the game on every `game:changed` except the scene edits (`SCENE_EDIT_KINDS`: the GM edits often, and they don't change the lobby; an edit that copied something into the library bumps the library instead), shows who is in the lobby (`OnlineDot` by the GM and by each seated player), keeps the GM's incoming log entries for the journal (newer than the loaded first page, they go on top without losing loaded pages; too many missed — the journal reloads), and replaces itself with `LobbyClosed` when the game is deleted or the viewer is removed from a closed game. The GM's header buttons are `MasterActions`: «Начать встречу» / «Закончить встречу» first, «Журнал», «Библиотека», and «Удалить игру» in the «Ещё действия» menu. A running session shows «Идёт встреча» next to the role for everyone, and a seated player gets a line that their sheet is closed until it ends. `TakeSeatModal` picks an own player character (NPCs are left out) and the «Можно передать управление» checkbox, on by default. The GM's «Журнал» opens `GameJournal`, a right-side drawer (full width below `xs`) that will also open over the 3D scene later: newest entries first, «Обновить» and «Показать ещё» (`useGameJournal`; the drawer unmounts its content when closed, so each opening reloads), each entry an accordion item (`GameEventItem`) whose panel shows the number, the kind and the raw `intent` and `result` JSON for debugging. The GM's «Библиотека» opens `GameLibrary`, a drawer of the same kind over the game library (`useGameLibrary`; it reloads when a `game:changed` of kind `session.started` or `library.refreshed` arrives while open): kind chips with counts, the name search, rows (`LibraryRow`) with the copied thumbnail, the kind and category, a badge «Изменена в справочнике» or «Нет в справочнике», and «Обновить» only on a changed copy. A row opens `LibraryEntryCard` in the same drawer (a trail of opened cards with «← Назад» / «← К библиотеке»): the copied image, kind, author, when copied and refreshed, the catalog check with «Обновить из справочника», the description, sources and the links by group (`libraryLinkGroups`: a monster's abilities, gear and effects, a pack's contents, an ability's step effects), each opening its own card or reading «Скрыто или удалено»; an NPC copy shows its items (with «в хранилище»), abilities and effects. Full cards (the stat block, ability steps, the NPC sheet) come with stage 8, when the game reads them. Below the seats the GM has the «Сцены» block (`GameScenes/`: `useGameScenes`, `SceneRow`, `AddSceneModal`): the «Открыта игрокам» switch (off while there is no active scene), «Добавить сцену» (a Select of own maps with their size; the scene is a copy, so later map edits don't reach it), and a row per scene — «Активная» with «К сцене», others «Сделать активной», «Перезапустить» in the row's menu after a confirm (disabled once the map is deleted). It re-reads itself on every `scene.*` change. A player sees `SceneInvite` («Мастер открыл сцену «…»» with «К сцене») while the scene is open, and a `scene.opened` change takes players straight to the scene page; the GM is never moved.
    - `pages/GameScenePage/` (`/games/:id/scene`) — the active scene in 3D, view only: the same lazy `MapScene` with `objectImages` from `sceneObjectImages`, the camera from the address like the map page, and `SceneSidebar` (laid out like the map page's: «← В лобби», the scene and game names, the GM's «Открыта игрокам» switch with a hint, the height cut). `useGameScene` loads the game and the scene (a 404 shows «В игре нет активной сцены», a 403 sends the player to the lobby) and keeps the camera frame while the scene id stays the same. `SceneRoom` joins the room once the game is loaded: a player goes to the lobby on `scene.closed`, and every `scene.*` change re-reads the scene (activated or restarted shows the new one). `MapScene` takes `objectImages` (`ObjectImagePaths`: monster, item and NPC thumbnail paths; the map editor keeps the catalog default) and `hideContainerContents` (from `GameSceneView.contentsHidden`): a player's chest is labelled by its name only, without «предметов: 0» or the overload warning.
  - `bookmarks/` — bookmarks (plan: [plan/done/bookmarks.md](plan/done/bookmarks.md)). `TitleWithBookmark` puts the star (`BookmarkButton/`, `useBookmark`: unknown state → disabled, busy, error under the star) next to the title of the item card (`ItemDetails`), the ability/effect card (`SimpleViewPage`, kind from `def.bookmarkKind`), the monster card (`MonsterHeader`) and the character sheet (`SheetHeader`). The «Закладки» page is `pages/BookmarksPage/`: kind chips and the name search in the URL (`?kind=&q=`, `bookmarkFilters.ts`), sections by kind, a placeholder row «Автор закрыл доступ» with «Убрать». The target's link and thumbnail are built in the page (`bookmarkTargetView.tsx`), not in `bookmarks/`: the item, catalog and character features import the star, so importing them back would close a cycle. The header links («Персонажи · Карты · Справочник · Закладки») fold into the burger menu below `md`.
  - `maps/` — map API client, `mapStateFromChunks` (API response → `MapViewState`: the shared `SizedMapState`, the blocks with the map size, plus the map objects), `useMapData` (load, edits, undo/redo), `mapSizeLabel` («32 × 32 клеток (160 × 160 фт)»). 3D view and the GM editor (see [plan/map.md](plan/map.md)):
    - `useMapData.ts` — one edit at a time (`busy`). An edit response carries the applied changeset (`MapEditResult.changes`); if its `seq` is exactly ours + 1, `applyMapChanges` applies it to a copy of the map (copy-on-write: only touched chunk arrays are new). If `seq` jumped (someone else, e.g. the AI, edited in between) or the changes don't fit our copy (conflicts, palette mismatch), the page refetches all chunks; a chunks response with an older `seq` is dropped. The map size lives in `state.size`, not in `info` (which goes stale after a resize): a resize changeset carries the size before and after, and `applyMapChanges` checks and updates it like the cells. Map objects ([plan/done/map-objects.md](plan/done/map-objects.md)) live in `state.objects` and go the same way: `applyMapChanges` copies them, and an object conflict also means a refetch. `refs` holds the names, images and sizes the objects point to (or placeholders); it comes with `/chunks` and is merged with the `refs` of every edit response. `frame` is the map area at open time, up to the top block: the camera is placed from it, never from live bounds, so neither edits nor a resize reset the camera. `applyOps`, `undo` and `redo` return nothing (the error goes to `editError`); `editOps` returns whether the edit went through, for the size panel to close only on success.
    - `render/buildChunkMesh.ts` — pure mesher: one geometry per chunk from the faces that are actually visible, box shapes included. It reads neighbours through the whole store so chunk borders cull correctly, splits transparent blocks into their own geometry, and takes the height cut and the map size as parameters (rebuild, not a clipping plane, so cut walls get tops; blocks hidden past the east or south edge are air for drawing and for their neighbours, so the edge shows a wall). Vertex colours go through `THREE.Color`, which converts sRGB to linear. Covered by unit tests, including face winding.
    - `cameraView.ts` — camera and height cut from the page URL (`?view=north&y=3`, or `cam=x,y,z&target=x,y,z`): one link always gives the same picture, which is how the AI agent looks at a map (see [mcp.md](mcp.md)). The cut slider writes `y` back to the URL (`replace`); the camera memo depends only on `view`/`cam`/`target` and the open-time frame, so neither the slider nor edits reset the user's camera. ## API access

- Base URL: `VITE_API_URL`, default `http://localhost:3000/api` in dev; the Docker build bakes in `/api` (same origin).
- Every request uses `credentials: 'include'` — auth lives in httpOnly cookies (see [server auth](server.md#auth)).
- Errors become `AuthApiError(status, message)`; the server's `message` is shown to the user as-is, so server-side user-facing messages are in Russian.
- `AuthProvider` bootstraps the session: `GET /auth/me`, on 401 `refreshSession()` and retry. It also subscribes to `onSessionExpired` and drops the user when a refresh is rejected, so `RequireAuth` sends them to the login page. The access cookie lives 15 minutes, so without the refresh in `apiRequest` client-side navigation would start failing with «Access token missing». The bootstrap promise is module-level on purpose — StrictMode mounts effects twice, and a duplicate refresh would be rejected because the first one rotated the token.
- **Sign-in through lolka** (`features/auth/LolkaSignIn/`): under the login and register forms, «или» and a «Войти через лольку» button in lolka's colours: a teal gradient (its light end darker than on the app icon, so white text keeps a 4.5 contrast) and the lolka icon (`lolka-icon.webp`, 96 px, downscaled from the app icon). It shows only when `GET /auth/providers` says `lolka: true` (off locally: lolka accepts one return address, production's). The button is a plain link to `${API_BASE_URL}/auth/lolka/start`, not a `fetch`: the browser goes to lolka and comes back through the server, which sets the cookies and redirects to `/`. A failure comes back as `/login?lolkaError=<code>`; `LoginPage` shows `lolkaErrorMessage(code)` in its usual error alert and strips the parameter. Plan: [plan/done/lolka-login.md](plan/done/lolka-login.md).
- **Profile** (`/profile`, `pages/ProfilePage/`): reached through the menu under the nickname in the header («Профиль»; «Выйти» is there too). Shows the nickname and whether lolka is connected; an account without a password gets `SetCredentialsForm` (login + password, after which the login in `AuthContext` is updated), one with a password sees its login and `ChangePasswordForm`. Below is «Настройки» (`SettingsCard`): «Взгляд на карте» as three `Radio.Card`s with an SVG preview of the stand from above (`FacingMarkerPreview`). A choice saves at once, without a button: the user in `AuthContext` changes before the `PATCH /profile/settings` answer, the cards are disabled while it runs, and an error puts the previous choice back with the server's message under the cards.

## UI changes: UX and the browser check

The rule itself is in [CLAUDE.md](../CLAUDE.md#ui-changes-appsweb); this is the how-to.

### UX before coding

Questions to answer before writing the component:

- **Place.** Which existing group does it belong to? Look at how the neighbouring pages already do it and follow that: map tools go on the scene (`SceneToolbar`) and their settings into `MapSidebar`, red is kept for errors and delete buttons. A new control next to related ones beats a new control where there happened to be room.
- **Discoverability.** Can the person find it without being told? A text label beats a bare icon; an icon-only button needs a tooltip. Add a hotkey only for frequent actions and only if it fits the existing ones (`useMapEditor`: Ctrl+Z, Ctrl+Shift+Z / Ctrl+Y, Esc, 1–8, R, Del; the camera: Q/E). Letters and digits go by `event.code` (`useKeyCodes`), so they work in the Russian layout.
- **Feedback.** What does the person see while it's working, when it fails, when there's nothing to show, and when the action is unavailable (and why)? Anything that destroys data asks for confirmation.
- **Effort.** Count the clicks and the mouse travel for an action done often; keep sensible defaults so the common case needs no setup.
- **Consistency.** Mantine components and theme colours (`src/theme/`), not one-off styles; wording in the same tone as the neighbouring strings.
- **Narrow screen and both schemes.** On `/maps/:id` the panel moves under the scene; light is parchment, dark is charcoal + brass.

If that leaves one clear answer, build it and mention the reasoning in the summary. If it leaves two or more with real tradeoffs (e.g. a toolbar button vs. a context menu item), ask the user first, with the options sketched and one recommended.

### Browser check

1. Start the stack: `pnpm dev` (web on `:5173`, API on `:3000`; needs the local Postgres).
2. Open the page with the Playwright MCP (wired up in `.mcp.json`) and log in under the local test account. Its credentials are deliberately not in the repo: they live in the Claude Code session memory of this project. If there is none, register a throwaway account on the local stack and tell the user.
3. Function: go through the new flow the way a person would, from the entry point to the result, plus at least one error or edge case (empty input, cancelled action, server error). Then read the browser console and the failed network requests.
4. Looks: take screenshots and look at them. Check alignment, spacing, overflow and clipped text, in both colour schemes (header toggle), and at a narrow width (`browser_resize`) when the layout responds to it.
5. Map pages: set the camera through the URL (`view` or `cam`/`target`, plus `y`), wait for «Сцена готова», then take the screenshot, one call after another (see [mcp.md](mcp.md)). In the local Playwright the first screenshot after loading a page sometimes shows the previous paint (an empty canvas without «Центр: y») although the DOM is ready; take it again before calling the scene broken. Don't move the camera with the mouse.
6. Fix what the check finds and repeat it. If it couldn't run, say so in the summary.

## Gotcha: Git Bash on Windows

Git Bash rewrites `VITE_API_URL=/api` into a Windows path (`C:/Program Files/Git/api`). For a local production-like build prefix the command with `MSYS_NO_PATHCONV=1`. Docker builds on Linux are unaffected.
