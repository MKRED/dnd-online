# Предметы: набор снаряжения

Живой документ: решения, открытые вопросы и чеклист этапов. Отмечаем сделанное по ходу работы (`[x]`). Составлен 2026-10-14. Продолжение [items.md](items.md) (категория 6 в таблице) и [items-filters.md](items-filters.md).

## Что делаем

Категория «Набор снаряжения» (`pack`). Набор — это предмет каталога, в составе которого лежат **другие предметы каталога с количеством**: «Набор путешественника» — рюкзак, спальник, масло ×2, рационы ×10, верёвка, трутница, факелы ×10, бурдюк.

Это первая категория, которая ссылается на другие предметы. Поэтому она сложнее предыдущих: ссылка может указывать на чужой, скрытый или удалённый предмет. Распаковка набора в инвентарь персонажа пока не делается, она появится вместе со связкой инвентаря и предметов ([items.md](items.md), «Позже»). Состав набора нужно хранить так, чтобы эту распаковку потом можно было сделать без переделки.

## Что нашли в источниках

Проверено 2026-10-14. Таблица всех семи наборов 2024 года и расхождения источников — в [dnd/items.md](../dnd/items.md), раздел «Наборы снаряжения». Для этого плана важно:

- **Цена и вес у набора свои, как у любого предмета.** Общего правила о наборах в книге нет.
- **Состав — плоский список** «предмет × количество». Наборов внутри наборов в книге нет.
- **Количество — целое число в единице самого предмета:** масло ×7 фляг, бумага ×5 листов, рационы ×10 (на 10 дней). Это сходится с тем, как в каталоге заводят такие предметы: «Масло (фляга)», «Рацион (1 день)».

## Принятые решения

Хранение, публикация, вес, удаление и скрытие решены с пользователем 2026-10-14. Остальное — очевидные следствия; если что-то не так — скажите.

### Хранение состава — отдельная таблица

Решено с пользователем: отдельная таблица с внешними ключами, «чтобы полностью контролировать процесс».

```
item_pack_entries
  pack_id   uuid → items.id  ON DELETE CASCADE   -- удалили набор — его строки тоже
  item_id   uuid → items.id  ON DELETE CASCADE   -- удалили предмет — он пропадает из наборов
  quantity  integer, CHECK 1..1000
  position  integer                              -- порядок строк, как его задал автор
  PRIMARY KEY (pack_id, item_id)                 -- один предмет — одна строка
```

- **Миграция** `0018_item_pack_entries` идёт в прод-базу. **Перед `db:migrate` спрашиваем пользователя.**
- **Форма API не меняется.** У набора, как у других категорий, состав приходит и уходит в `details` (`details.contents`). Сервер в одной транзакции пишет предмет с пустым `details` в `items` и заменяет его строки в `item_pack_entries` целиком. Так размеченное объединение в `shared` остаётся единообразным, а форма шлёт один `PUT`.
- **Индекс по `item_id`** нужен для запроса «в каких наборах лежит предмет». Этот запрос нужен при удалении и скрытии (см. ниже).

### Ограничения состава

Сервер проверяет при создании и правке:

- **Число строк:** от 1 до 50. Пустой набор не имеет смысла: «Набор» без состава — это просто «Базовый». 50 строк с запасом: в самом длинном наборе книги, у дипломата, 11 строк.
- **Количество:** целое, от 1 до 1000 (как верхняя граница насыщения).
- **Один предмет — одна строка:** повтор отклоняется. В форме повторно выбранный предмет не добавляется, а увеличивает количество.
- **Ссылаться можно только на предметы, которые автор набора видит сейчас:** свои (и скрытые тоже) и опубликованные чужие. Иначе 400 «Предмет из состава не найден». Так нельзя подсмотреть чужой скрытый предмет, перебирая id.
- **Набор в наборе запрещён**, как и в книге. Заодно это исключает циклы.
- **Категорию набора можно сменить** на другую: его строки удаляются в той же транзакции.

### Публикация — только с опубликованным составом

Решено с пользователем: опубликовать набор нельзя, пока в составе есть неопубликованные предметы. Пользователю сразу предлагают опубликовать их.

- **Сервер.** Набор с `isPublic: true` и скрытыми предметами в составе получает 409 «Сначала опубликуйте предметы из состава: Факел, Верёвка». Скрытый набор со скрытыми предметами сохраняется как обычно.
- **Форма.** При «Сохранить» с включённым «Показывать в каталоге» форма сама видит свои скрытые предметы в составе: у каждой строки известен `isPublic`. Тогда она не отправляет запрос, а показывает уведомление:

  ```
  ┌───────────────────────────────────────────────────────────┐
  │ В составе 2 скрытых предмета: Факел, Верёвка.             │
  │ Набор можно опубликовать только вместе с ними.            │
  │                   [Опубликовать всё и сохранить] [Отмена] │
  └───────────────────────────────────────────────────────────┘
  ```

  «Опубликовать всё и сохранить» шлёт тот же `PUT` с флагом `publishContents: true`. Сервер в одной транзакции публикует **свои** скрытые предметы из состава и сохраняет набор: либо всё, либо ничего. Отдельные `PUT` на каждый предмет не нужны, и набор не останется опубликованным наполовину.

- **Чужой предмет, скрытый уже после того, как его положили в набор,** опубликовать за автора нельзя. Такую строку автор набора должен убрать: сервер отклонит её как «не найден» (правило выше).

### Удаление предмета, который лежит в наборах

Решено с пользователем: предмет удаляется и пропадает из всех наборов (`ON DELETE CASCADE`).

- **Подтверждение удаления перечисляет, где лежит предмет:** «Предмет лежит в 3 наборах: Набор путешественника, Набор взломщика и ещё 1 чужой. Из них он тоже пропадёт.» Свои наборы — по названию, чужие — числом: их названия могут быть скрыты.
- **Откуда берётся перечень.** Для этого `GET /items/:id` отдаёт **автору** `packs: { mine: { id, name, isPublic }[]; othersCount: number }`. Остальным не отдаёт: им незачем знать, где ещё лежит чужой предмет.
- **Если из набора удалили последний предмет,** набор остаётся с пустым составом. Карточка показывает «Состав пуст», а при следующем сохранении форма попросит что-то добавить.

### Скрытие предмета, который лежит в опубликованных наборах

Решено с пользователем: скрывать можно.

- **В чужих наборах** строка становится «Предмет скрыт автором», без названия и ссылки. Чужой набор остаётся опубликованным: автор набора не должен терять публикацию из-за чужого действия.
- **Свои опубликованные наборы с этим предметом** форма предлагает скрыть вместе с ним. Уведомление того же вида, что при публикации:
  - текст: «Предмет лежит в опубликованных наборах: Набор путешественника. Скрыть и их?»;
  - кнопки: [Скрыть всё] [Скрыть только предмет];
  - «Скрыть всё» шлёт флаг `hidePacks: true` в том же `PUT`, одной транзакцией.
- **Список наборов** форма берёт из того же `packs` в ответе `GET /items/:id`.

### Что видит читатель

Сервер в ответе кладёт в каждую строку состава краткую карточку предмета, но только если читатель видит этот предмет. Тогда клиенту не нужен отдельный запрос на каждую строку.

```ts
interface PackEntry {
  itemId: string;
  quantity: number;
  // null — предмет скрыт автором от читателя (удалённый пропадает из состава сам)
  item: {
    name: string;
    category: ItemCategory;
    weight: number;
    isPublic: boolean;
    image: ItemImageMeta | null;
  } | null;
}
```

- **Строка с `item: null`** показывается как «Предмет скрыт автором × 2».
- **В форме у автора набора** такая строка тоже видна и помечена, её можно убрать. Сохранить набор с ней нельзя (правило выше), поэтому форма подсвечивает строку ещё до отправки.
- **Список `/items` тоже отдаёт состав с карточками:** все наборы списка разворачиваются одним запросом к таблице, это не тяжело. Сетка и список состав пока не показывают, но форме набора он нужен уже в списке (вес состава). Решено при реализации этапа 1.

### Вес и цена набора

Решено с пользователем: вес вводится вручную, рядом — подсказка, сколько весит состав.

- **Вес и цена набора — общие поля,** как в книге: у набора путешественника 55 фнт. и 10 ЗМ.
- **Подсказка под полем «Вес»** у набора: «Состав весит 55 фнт.».
  - Это сумма `вес × количество` по строкам, которые видны в форме.
  - Строки «Предмет скрыт автором» в сумму не входят. Если такие есть, подсказка: «Состав весит не меньше 50 фнт.».
  - Пересчитывается сразу при правке состава.
- **Цену не суммируем.** В книге набор, похоже, продаётся по своей цене, а не по сумме. Это не проверено.

### Интерфейс

- **Форма.** При категории «Набор снаряжения» под категорией появляется блок «Состав»:
  - **строки состава:**
    - миниатюра и название;
    - поле количества (`NumberInput`, 1–1000);
    - кнопка «Убрать» (иконка с подписью для экранного диктора);
    - у своей скрытой строки — пометка «Скрыт», как в «Моих».
  - **выбор предмета:**
    - над списком — поле поиска предмета (`Select` с `searchable`) по своим и опубликованным предметам, без наборов и без самого набора;
    - выбранный предмет сразу добавляется строкой с количеством 1, повторный выбор увеличивает количество;
    - варианты берутся из тех же запросов `/items?scope=mine` и `scope=catalog`, что и каталог. Отдельного поиска на сервере не нужно: фильтры каталога уже работают на клиенте.
  - **пустой состав:** подсказка «Добавьте предметы — например, рюкзак и верёвку», а при сохранении ошибка «Добавьте в набор хотя бы один предмет».
- **Карточка.** Раздел «Состав» под полями: строки с миниатюрой, названием и «×10», каждая строка — ссылка на карточку предмета. Скрытая строка — серым, без ссылки.
- **Подтверждения удаления и скрытия** — с перечнем наборов (см. выше).
- **Сетка и список каталога.** Бейдж категории, как у остальных; число предметов в наборе не показываем.
- **Узкий экран.** Строка состава в форме не переносится, название обрезается многоточием, поле количества узкое (около 72 px).

## Открытые вопросы

- **Распаковка в инвентарь** — не в этом плане. Когда до неё дойдём, решим, копировать набор в инвентарь как один предмет или сразу его состав.
- **Предмет, который лежит в чужом наборе, не может стать набором,** а убрать его из чужого набора автор не может. Пока считаем это редким случаем: автор может завести новый предмет-набор.
- **Тестовые предметы при проверках** попадают в прод-базу — удаляем за собой.
