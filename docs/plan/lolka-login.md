# Вход через лольку (OAuth 2.0): решения и план

Живой документ: принятые решения, открытые вопросы и чеклист этапов. Отмечаем сделанное по ходу работы (`[x]`). Составлен 2026-10-14.

## Что делаем

Кнопка «Войти через лольку» на странице входа, рядом с логином и паролем. Вход по паролю остаётся как есть.

Источник: инструкция лольки https://lolka.aoshi.ru/docs/login.html (прочитана 2026-10-14). Правил DnD здесь нет.

## Что даёт лолька

- **Протокол** — OAuth 2.0 Authorization Code с PKCE (`S256`). `scope` нет.
- **`GET https://lolka.aoshi.ru/oauth/authorize`** — сюда браузер уходит с параметрами:
  - `response_type=code`;
  - `client_id` (вида `la_…`);
  - `redirect_uri`;
  - `state` (случайная строка против CSRF);
  - `code_challenge = BASE64URL(SHA256(code_verifier))` без `=`;
  - `code_challenge_method=S256`.
- **`POST /oauth/token`** — запрос с сервера, `application/x-www-form-urlencoded`. Поля:
  - `grant_type=authorization_code`;
  - `code`;
  - `redirect_uri`;
  - `client_id` и `client_secret` (можно вместо этого передать заголовком `Authorization: Basic`);
  - `code_verifier`.

  Ответ: `{ access_token, token_type: "Bearer", expires_in: 3600 }`. Refresh-токена нет.
- **`GET /oauth/userinfo`** с `Authorization: Bearer …` возвращает:
  - `sub` — постоянный id пользователя, свой для каждого сайта;
  - `nickname`;
  - `avatar_url` (может быть `null`);
  - `is_adult` (`true` / `false` / `null`).
- **Ограничения:**
  - код живёт 60 секунд и одноразовый: повторное предъявление отзывает выданный по нему токен;
  - `redirect_uri` сверяется посимвольно;
  - 60 запросов в минуту с одного IP.
- **Ошибки:**
  - `/oauth/token`:
    - 401 `invalid_client` — неверные `client_id` или `client_secret`;
    - 400 `invalid_grant` — код использован или истёк, не совпал `redirect_uri` или `code_verifier`, либо доступ отозван;
    - 400 `unauthorized_client` — приложение приостановлено или запрос пришёл не с разрешённого IP;
  - `/oauth/userinfo`: 401 `invalid_token`;
  - любой адрес: 429 — превышен лимит запросов.
- **Заявка подаётся в приложении лолька:**
  - вид: «только вход» или «в каталоге»;
  - адреса возврата;
  - тестовый доступ для проверки;
  - подтверждение домена файлом `https://<домен>/.well-known/lolka-app.txt`. В файле строка `lolka-app-<32 символа>`. Файл открывается без редиректов, удалять его нельзя: лолька перепроверяет его раз в сутки;
  - `client_secret` показывают один раз;
  - не больше 2 заявок за 30 дней.

Сверено со страницей через пересказ, а не построчно. Перед этапом 2 перечитать оригинал (особенно ответы с ошибкой на `redirect_uri`).

## Принятые решения

### Решено с пользователем 2026-10-14

- **Основа — наша таблица `users`.** Все данные приложения (персонажи, карты, токены) висят на `users.id`, а лолька только подтверждает, кто пришёл.
- **Первый вход через лольку создаёт полноценный аккаунт**, если `sub` ещё ни с кем не связан. Позже владелец может задать ему логин и пароль и входить через браузер без лольки (этап 4).
- **Заявка — «только вход».** Каталог и вход внутри приложения лольки — потом (этап 6).
- **Ник берём из лольки только при создании аккаунта**, дальше он наш и не синхронизируется.
- **Аватар и `is_adult` пока не используем.**
- **Привязка старых аккаунтов с паролем к лольке — отдельный этап, не сейчас** (этап 5). Пока вход через лольку всегда ведёт в свой аккаунт.
- **Локально вход через лольку не проверить:** в заявке только один адрес возврата, прод. Поток покрываем тестами с подменой лольки, настоящий вход проверяем на проде после деплоя.
- **Логин и пароль задаются на новой странице «Профиль»** (`/profile`), пункт в меню пользователя рядом с API-токенами. Потом туда же лягут смена ника и привязка лольки.

### Весь поток идёт через сервер, без страниц-посредников в SPA

1. Кнопка — обычная ссылка `GET /api/auth/lolka/start`, полный переход страницы, а не `fetch`. Сервер:
   - генерирует `state` и `code_verifier`;
   - кладёт их в короткоживущую cookie `lolka_oauth`: `httpOnly`, base64url от JSON (без подписи: подделать её мог бы только тот, кто ставит cookie на наш домен, а против него подпись не помогла бы — он подставил бы свою настоящую), `sameSite: lax`, `path=/api/auth/lolka`, 10 минут;
   - отвечает 302 на `/oauth/authorize`.
2. Лолька возвращает браузер на `GET /api/auth/lolka/callback?code&state`. Сервер:
   - сверяет `state` с cookie и стирает cookie;
   - меняет код на токен, получает `userinfo`;
   - находит или создаёт пользователя;
   - ставит наши обычные `access_token` и `refresh_token` (`TokenService.setAuthCookies`);
   - отвечает 302 на `/`.
3. При любой ошибке — 302 на `/login?lolkaError=<код>`, страница входа показывает понятное сообщение.

Почему так:
- `client_secret` и обмен кода остаются на сервере, как требует лолька;
- серверных сессий у нас нет, а подписанная cookie их заменяет;
- `sameSite: lax` пропускает cookie при возврате с лольки, потому что это переход верхнего уровня методом GET;
- токен лольки нам нужен один раз, ради `userinfo`, поэтому его не храним.

CSP helmet не мешает: это навигация и редиректы, а не загрузка скриптов. Скрипт `lolka-web-app.js` понадобится только для входа внутри приложения (этап 6), и тогда расширим `script-src`.

### Связь с аккаунтом — отдельная таблица `user_identities`

- **Поля:**
  - `provider` (`'lolka'`);
  - `subject` (`sub` лольки);
  - `user_id` → `users.id`, с `on delete cascade`;
  - `created_at`.
- **Уникальность:** `unique(provider, subject)` — один аккаунт лольки ведёт ровно в одного пользователя; `unique(user_id, provider)` — у пользователя не больше одной лольки.
- **Почему не колонка в `users`.** Таблица не трогает существующих пользователей, а второй способ входа (если появится) ляжет в неё без миграции `users`.
- **`users.password_hash` становится nullable.** Тому, кто пришёл через лольку, пароль не нужен. `AuthService.login` надо поправить: без хэша сразу отвечать «неверный логин или пароль», не вызывая `bcrypt.compare`, иначе он упадёт на `null`.
- **`users.login` остаётся обязательным и уникальным.** Он лежит в JWT payload, в ответе `/auth/me` и в api-токенах. Новому пользователю из лольки генерируем технический логин `lolka_<8 символов>`. Пользователь его не видит и не вводит; показываем везде `nickname`.

### Вызовы лольки — отдельный сервис с логами и таймаутом

`LolkaOAuthService` в модуле `auth` (или своя папка `auth/lolka/`, если файлов станет больше двух):
- `fetch` с `AbortSignal.timeout(10_000)`;
- pino-логи по конвенции: начало, `durationMs`, итог;
- сам токен и секрет в лог не пишем.

### Настройки — env

`LOLKA_CLIENT_ID`, `LOLKA_CLIENT_SECRET`, `LOLKA_REDIRECT_URI`, `LOLKA_BASE_URL` (по умолчанию `https://lolka.aoshi.ru`).

Если `LOLKA_CLIENT_ID` не задан, вход через лольку выключен:
- маршруты отвечают 404;
- `GET /api/auth/providers` отдаёт `{ lolka: false }`, и кнопку не показываем.

Так dev и тесты работают без секретов.

### Подтверждение домена — блоком в edge-nginx

Отдавать `/.well-known/lolka-app.txt` из Nest неудобно: `serve-static` по умолчанию игнорирует пути с точкой (`dotfiles: 'ignore'`), а код подтверждения — не дело репозитория.

Добавляем `location = /.well-known/lolka-app.txt { return 200 "lolka-app-…\n"; }` в `dnd.aoshi.ru.conf` на хосте. Так же, как `client_max_body_size`, см. [deploy.md](../deploy.md). Лолька сама предлагает nginx-блок в заявке.
