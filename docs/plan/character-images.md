# Картинки персонажа: решения и план

Живой документ: принятые решения, открытые вопросы и чеклист этапов. Отмечаем сделанное по ходу работы (`[x]`). Составлен 2026-10-14.

## Что делаем

- **Галерея** — у персонажа несколько картинок (арты, референсы).
- **Основная картинка** — одна из галереи, «лицо» персонажа.
- **Миниатюра** — квадратный фрагмент основной картинки, который пользователь выбирает сам и может поменять. Её показываем в списке персонажей, позже она же станет портретом в игре и на токене.
- **Просмотр** — картинка открывается на весь экран поверх страницы, с листанием и увеличением.

Правил DnD здесь нет, сверять не с чем.

## Принятые решения

### Файлы храним в Postgres (`bytea`)

Решено с пользователем 2026-10-14.

- **Почему.** Локальная разработка и прод смотрят в одну базу ([deploy.md](../deploy.md)). Если класть файлы на диск, картинка, загруженная локально, в проде окажется битой: строка в базе есть, файла нет. В базе этой проблемы нет, бэкап базы включает картинки, деплой и `docker-compose.yml` не меняются. `bytea` у нас уже есть — чанки карты (`map_chunks`, `customType`).
- **Цена.** База растёт. Держим это лимитами и сжатием (см. «Обработка на сервере»): одна картинка — порядка 200–500 КБ, 20 картинок на персонажа — до ~10 МБ.
- **Отклонено:** диск с volume (битые картинки между dev и prod, чистка файлов при удалении), MinIO/S3 (новый сервис и ключи ради десятков файлов).

### Картинки видит только владелец, грузим их через `fetch`

Решено с пользователем 2026-10-14.

- **Почему не обычный `<img src="/api/…">`.** Access-токен живёт 15 минут, и обновляет его только `apiRequest` (ответ 401 → refresh → повтор). Тег `<img>` так не умеет: через 15 минут картинки молча перестали бы грузиться.
- **Как.** Клиент запрашивает байты через тот же механизм, что и остальной API (с refresh), получает `Blob` и показывает его через `URL.createObjectURL`. Маршруты картинок закрыты `AuthGuard` и проверяют владельца, чужая картинка — 404, как у персонажей.
- **Следствия:**
  - в `apiRequest.ts` сейчас только JSON: нужен вариант для бинарного ответа и отправка `FormData` без `Content-Type: application/json`;
  - CSP helmet по умолчанию — `img-src 'self' data:`. `blob:` туда надо добавить (`main.ts`), иначе в проде не покажется ничего; в dev этого не видно, потому что там страницу отдаёт Vite без CSP — **проверять на собранном сервере**;
  - нужен кеш object URL на клиенте (один запрос на картинку, `revokeObjectURL` при уходе со страницы), иначе утечка памяти и повторные загрузки;
  - сервер отвечает `Cache-Control: private, max-age=31536000, immutable`: содержимое картинки по её id не меняется, а у миниатюры в адресе версия (`?v=`).
- **Что откладываем.** Показ портрета другим игрокам появится вместе с игрой: тогда право чтения расширится до участников игры. Схема этому не мешает.

### Галерея доступна после создания персонажа

Решено с пользователем 2026-10-14.

- На странице создания персонажа ещё нет в базе, прикреплять не к чему. Там — короткая подсказка «Картинки можно добавить после создания».
- После создания открываем страницу редактирования этого персонажа (сейчас — список с бейджем «Новый»), где галерея уже работает.

### Обработка на сервере: `sharp`

Загруженный файл не храним как есть — перекодируем:

- принимаем JPEG, PNG, WebP, до 10 МБ; тип определяет сам `sharp` по содержимому, а не по расширению и `Content-Type`;
- поворачиваем по EXIF и выбрасываем метаданные (в фото бывает геометка);
- сохраняем три варианта в WebP:
  - `full` — вписан в 2048×2048, для просмотра;
  - `preview` — вписан в 480×480, для сетки галереи и ленты просмотрщика;
  - `thumb` — 256×256, вырез миниатюры. Делается для каждой картинки, а не только для основной (поправка к первому варианту плана): это около 10 КБ, зато «Сделать основной» — просто смена флага, без чтения и перекодирования файла;
- оригинал не храним: `full` достаточно для экрана, а место экономим;
- защита от «бомб»: `limitInputPixels` (около 50 Мп), анимацию не поддерживаем (берётся первый кадр);
- лимит — 20 картинок на персонажа и 10 МБ на файл (одобрено пользователем 2026-10-14). Это константы в `packages/shared/src/characterImages.ts`, общие для формы и сервера, а не env, как задумывалось: лимит размера нужен multer в декораторе маршрута, который выполняется раньше, чем `ConfigModule` читает `.env`.

### Миниатюра — это вырез, а не отдельный файл

- Храним прямоугольник выреза `{ x, y, size }` в пикселях варианта `full` (он неизменен) и по нему сервер рендерит `thumb`. Поэтому миниатюру можно открыть и поправить, а не выбирать заново.
- По умолчанию — квадрат по центру (у вертикальных картинок сдвинут к верху: лицо обычно там). «Умный» вырез `sharp` (`attention`) не берём: он не сообщает, какой прямоугольник выбрал, и редактор открылся бы не на том месте.
- Вырез хранится у каждой картинки, поэтому при возврате прежней основной её миниатюра сохраняется.

### Основная картинка

- Первая загруженная становится основной сама — частый случай без лишних кликов.
- При удалении основной ею становится следующая по порядку; если картинок не осталось — у персонажа нет портрета (заглушка с инициалом).
- В ответ `Character` добавляем `mainImage: { id, version } | null`, чтобы список персонажей знал, что грузить, без запроса галереи.

### Место в интерфейсе

- **Страница редактирования:** отдельный блок «Картинки» над формой, **вне `<form>`**. Форма сохраняется кнопкой внизу, а картинки — сразу; внутри формы это путало бы («загрузил, не нажал „Сохранить“ — пропало?») и кнопки блока отправляли бы форму. Под заголовком блока — «Картинки сохраняются сразу».
- **Сетка** плиток-превью + плитка-зона загрузки («Перетащите картинки или нажмите»). Пустая галерея — одна большая зона загрузки.
- **Плитка:** клик открывает просмотр. Кнопка-меню «⋯» в углу, видна всегда (на телефоне нет наведения): «Сделать основной», «Изменить миниатюру» (у основной), «Удалить» (с подтверждением). У основной — бейдж «Основная».
- **Состояния:** загрузка — плитка с лоадером; ошибка файла (формат, размер, лимит) — текст рядом с зоной, на русском; несколько файлов грузим по очереди, ошибка одного не останавливает остальные.
- **Список персонажей:** миниатюра слева в карточке.
- **Форма миниатюры — квадрат со скруглёнными углами** (решено с пользователем 2026-10-14), и в списке, и в рамке редактора. Хранится обычный квадрат, скругление — только отображение.
- **Просмотр:** скачивание включено (`withDownload`, решено с пользователем 2026-10-14) — это картинки самого владельца.
- **Редактор миниатюры:** модальное окно — картинка под квадратной рамкой, двигаем и масштабируем (мышь, колесо, жесты), «Сохранить» / «Отмена».

**Обновление Mantine — обязательный первый шаг.** Пакеты Mantine требуют точно совпадающих версий (`@mantine/lightbox@9.7.2` → `@mantine/core@9.7.2`), а у нас 9.5.1. Поднимаем `core`, `form`, `hooks` разом и перепроверяем форму персонажа.

**Риски:**

- `@mantine/lightbox` молод (первая версия — 2026-08-31). Если встретим блокирующий баг — переходим на `yet-another-react-lightbox`; просмотрщик изолируем в одном компоненте, чтобы замена была дешёвой.
- `sharp` ставит нативные пакеты `@img/*`. На Windows установка и тесты проходят. **В Docker (`node:24-slim`, pnpm 11 с `allowBuilds`) ещё не проверено** — увидим при первом деплое; если сборка упадёт на `sharp`, смотреть `allowBuilds` в `pnpm-workspace.yaml`.

## Данные и API

### Таблицы

- `character_images` — метаданные: `id`, `character_id` (FK, `on delete cascade`), `position`, `is_main`, `width`, `height` (варианта `full`), `thumb_crop` (jsonb `{x, y, size}`), `thumb_version` (растёт при смене выреза), `created_at`. Частичный уникальный индекс по `character_id where is_main` — основная ровно одна. Указатель в `characters` не заводим, чтобы не было циклической ссылки.
- `character_image_files` — байты: `image_id` (FK cascade), `variant` (`full` | `preview` | `thumb`), `data bytea`; PK `(image_id, variant)`. Отдельная таблица, чтобы обычный `select()` метаданных не тащил мегабайты.
- Миграция обычная (`pnpm db:generate`). Применение идёт в прод-базу — перед `db:migrate` спрашиваем пользователя.

### Маршруты (все под `AuthGuard`, только владелец)

- `GET /characters/:id/images` — метаданные галереи.
- `POST /characters/:id/images` — `multipart/form-data`, поле `file`, один файл за запрос.
- `GET /characters/:id/images/:imageId/file?variant=full|preview|thumb` — байты.
- `PATCH /characters/:id/images/:imageId` — `{ isMain?: true, thumbCrop? }`.
- `DELETE /characters/:id/images/:imageId`.

Типы ответа (`CharacterImage`, `mainImage`) — в `packages/shared`. Сервер: отдельный модуль `apps/server/src/character-images/` — контроллер, чтение (`character-images.service.ts`), правки (`character-image-edit.service.ts`), обработка `sharp` (`image-processing.ts`), вырез (`thumb-crop.ts`). На загрузку — rate limit 40 в минуту с IP.

### Клиент

`apps/web/src/features/characters/CharacterGallery/`: блок галереи, плитка, зона загрузки, редактор миниатюры, просмотрщик, хук данных, кеш blob-адресов. `CharacterAvatar` — миниатюра для списка. `imageUrlCache.ts` + `useImageUrls.ts` — загрузка байтов и object URL со счётчиком пользователей.

Панель просмотрщика собрана своя (`toolbarItems`): штатная кнопка скачивания `@mantine/lightbox` назвала бы файл идентификатором из blob-адреса без расширения, наша сохраняет «<имя персонажа> <номер>.webp». Фон просмотрщика — глухой чёрный: штатные 90% на светлой теме пропускают страницу.
